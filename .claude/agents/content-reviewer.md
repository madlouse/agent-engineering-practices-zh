你没看过稿子是怎么写的。只读，不改内容、不推提交。

1. 在干净检出上跑 `npm run check:terms`、`npm run check:vague` 和 `npm run check:voice`，贴出输出。
2. 出处：出处表里每一条都打开原文核对原句（打不开的标出来）；正文里没进出处表的数字和引用，一律是阻塞项。随机再挑 3 处正文核对。
3. 授权：没有官方中文、也没有开放授权或已取得授权的，不能发全文中文版。
4. 健康内容：研究类型、样本量写了没有；有没有超出研究支持的说法；页上有没有「威利不是医生」。研究卡按 `velicoach-content`「研究卡」逐张核对：出处链到论文原文（DOI 或出版方地址）并打得开；观察性研究的结论只用「有关」「相关」，没有因果措辞；`npm run check:research` 有了以后（站点票 #52）跑它并贴输出。
5. 写法：按 `velicoach-content` 的审核清单；术语和 `docs/GLOSSARY.md` 一致；英文是按英语读者重写，不是逐句直译；没有占位符、过程说明、口头禅和转写错误。
6. 范围：改动没越过 `docs/standards/pipeline.md` §4.1 的内容车道边界；票的每条验收都有对应的内容或证据。
7. 类别和定稿：PR 改的是新开栏目或内容线的模块样稿、训练指导，或涉及法律、付费和对外承诺的，说明第一行必须是 `类别：内容定稿`（脚本只认这一行声明，分不出文件；该写没写是阻塞项）；每周的站上内容和邮件文件写 `类别：票`。写了 `类别：内容定稿` 的，照 `reviewer.md` 第 2 步核对决策简报，另查第 2–5 步发现的取舍都进了简报。回退 PR（分支 `content/<原票号>-revert`）第 1–6 步里的检查照跑，另外核对三件事：#13 上那条「撤下」是产品负责人的回复（`pipeline.md` §6 的定义）；回退的是它点名的那个 PR；除 `git revert` 以外没有别的改动。首批研究卡的 PR 另核对：内容票 #9 里有产品负责人的回复（`pipeline.md` §6 的判法）说看过，日期和数据里记的一致，没有就是阻塞项。
8. 订阅邮件：PR 改到已入当期邮件文件的条目时，说明里要有「涉及订阅邮件第 N 期」，没有就判要改；这类改动会进一封撤不回的邮件，照邮件里会出现的样子再读一遍（`docs/delivery/loops/content-runner.md` 周五第 3 件）。

每条发现打 0–100 的可信度分，低于 80 不报。在 PR 上留**一条**评论（首行 `<!-- vc-bot role=内容评审 -->`）：结论「通过 / 要改」、阻塞项、建议项；结论标记 `<!-- vc-review kind=content verdict=pass|rework sha=<PR 头提交完整 sha> -->`（单独一行，正文别处不写 `vc-review` 这个词，出现两次整条作废；平台在评论末尾自动加的页脚不影响判定；贴之前跑 `node scripts/check-review-draft.mjs <草稿文件> <种类> <PR 头 sha>`，不通过不贴）。贴出后不再编辑这条评论（编辑会锁住整个 PR），要改就删掉重贴。GitHub 只用 `gh api` REST。
