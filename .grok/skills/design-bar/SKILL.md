# Design Bar：Claude Design 的配套

## 分工

| 谁 | 负责什么 |
|---|---|
| **Claude Design · Design System 类型** | 设计语言的唯一来源：品牌手册（README）、token（多主题颜色、字号、间距、圆角）、组件规范与预览 |
| **Claude Design · Design 类型** | 方向稿、界面、交互稿：在画布上出、比较、修改 |
| **本技能** | Claude Design 不做的四件事：开工前确认、同步进仓库、检查实现代码、把评审沉淀回设计系统 |

为什么需要这一层：画布不会检查代码，写代码的 agent 也读不到私有画布，所以代码会悄悄长成另一套设计语言；而说不清需求时，直接出图会用品类默认值填空。本技能就是补这两个缺口，不重复做 Claude Design 已经做得更好的事（出图、风格瓦片、手写设计规范）。

## 决策原则

1. **以产品目标做决定。** 每个设计决定都回到同一个问题：它是否帮用户更容易达成目标，体验是否更简单、易懂、易上手、赏心悦目。
2. **问什么，定什么。**
   - 必须问用户的：产品意图（受众、核心任务、气质与品牌）、文档之间的方向冲突、难以撤回的大改（换品牌色、改信息结构）。
   - 自己决定的：体验和交互细节（反馈方式、动效、文案措辞、组件选择、状态处理）。以专业产品经理和设计师的身份直接决定，在 `decisions.md` 写明理由和被放弃的方案，交付时告诉用户「我决定了什么、为什么」；用户想改再改。
3. **一条意见代表一类问题。** 用户指出一个局部问题时，先找出它背后的原则，再检查所有同类位置（同一个组件的其他用法、同一类交互的其他时刻、同一条规则在其他页面），一次改完，并把原则写回设计系统。不要只改被指出的那一处。**但只改同一类缺陷**：不是同一类的「顺便优化」写成建议、等用户同意；用户只是在讨论时不动文件（`references/craft.md` §3.5）。
4. **模糊的要求先理解，再具体化。** 用户说不清时，先用自己的话复述理解并确认关键点；然后用专业判断把它变成具体、可检查的方案，而不是原样照做或反复追问。
5. **需求变了，设计同一轮跟上。** 产品决定一旦影响界面（改了说法、加了状态、换了交互），同一轮里改完设计系统、画板和需求文档的验收，并把旧说法记进词汇表（见「需求变更时」）。拖到下一轮，旧说法就会散落各处，靠记忆一定找不全。
6. **讲价值，不罗列功能。** 用户感受到的是「我的一天变成什么样」，不是功能清单。对比、方案页、引导页先用一个真实场景讲清差别，传统的功能对比放在后面或折叠起来。
7. **体验原则以 `references/ux-canon.md` 为总纲。** 两个术语（撤不回的动作、意图步）、九条原则（目的先行、熟悉的约定、只删不承载意图的步骤、即时回应和设计等待、能撤销就不确认、可信、连续不丢状态、替人办事的 Agent 也要能用、装饰要证明自己有用）和冲突时的先后；项目的规则表从它落数值。新提出的体验原则先在那里复核：和哪条重合、证据够不够、在哪不成立，再改规则。
8. **「好不好」和「对不对」一样要过门槛。** 体验与美学以苹果设计大奖的六个维度为标尺，每维有能判定的「中、强」条件；第一版和大版本定稿时，出口标准加一列「体验与美学」（动效原型和操作视频、六维不低于中、无障碍实测、步数实测）。这个奖只收 App Store 上的 App，网页把六维当内部标尺。口径和门槛见 `references/award-bar.md`。
9. **外壳全家一致。** 浅深色默认跟随系统；和别的产品共用入口时，按家族约定做导航和偏好记忆，改到共享的东西同一轮通知另一边（`references/family.md`）。

## 第 0 步：接入项目（代码仓库里才需要）

先看项目已有的约定：设计文档放在哪里（常见 `docs/design/`）、有没有现成的 token、skills 目录在哪里、有没有界面测试或组件预览可以离线渲染真实组件。然后运行：

```bash
python <本技能目录>/scripts/init_project.py <项目根目录> \
  --design-dir <设计目录，默认 design> --tokens-path <代码能直接引用的 tokens.css 位置>
```

它会创建设计目录模板、把本技能复制到项目的 skills 目录、在 `AGENTS.md` 写入设计规则（`CLAUDE.md` 通过 `@AGENTS.md` 引入）。可重复运行，不覆盖已有文件。skills 目录有索引时补一行。告诉用户改了哪些文件。

已有的设计文档、token、画布都是第 1 步的输入。**代码和设计文档描述的是两套不同的设计语言时，这本身就是必须让用户确认的问题。**

## 第 1 步：确认关键信息，不要猜

先自己读完能拿到的资料（PRD、设计文档、代码、截图、已有设计系统），再只问会改变设计含义的问题。七项：受众与场景、核心任务、品牌资产与不可改动项、气质、喜欢与讨厌的参考、平台与交付形式、内容来源。

- 先给「我的理解」表，让用户只做纠正；未知项用对比题问（附推荐和理由），一次最多 4 题。问法见 `references/intake.md`，形容词怎么翻译成参数见 `references/taste-lexicon.md`。
- 用户说「你来定」也算确认，记下选择和理由。
- **受众、核心任务、气质确认之前，不出完整设计。** 用户不在场时，做到第 2 步就停，列出待确认问题。
- 文档之间互相冲突时（比如 PRD 要求顶部放进度条，用户又要第一屏放任务），提出一个同时满足两边的方案并执行，同步更新冲突的那份文档（例如在 PRD 里加一条裁决），告诉用户。

结果写进 `<设计目录>/brief.md`，末尾写上**方向五行**（产品、气质、世界、高光时刻、签名，写法见 `references/craft.md` §1）。

## 第 2 步：标杆卡

把参考作品拆成可检查的标准，写进 `<设计目录>/bar-sheet.md`：体验关键词（意味着什么 / 不意味着什么）、参考拆解（可观察的事实）、3–5 条能检查的标杆原则、签名时刻、明确不做（具名反面模式见 `references/anti-patterns.md`）、底线。

参考要真的看：能用浏览器就截图；看不到就说明是基于一般认知。借「为什么好」，不照搬「长什么样」。参考里要有 3–5 个近年苹果设计大奖获奖或入围、任务相近的 App，写清借什么（`references/award-bar.md` 第 0 节），评审时和它们并排比。

## 第 3 步：在 Claude Design 里建立设计语言

用 Artifact 工具先列出用户已有的 Design System；标为默认的直接用，没有就新建一个（`references/claude-design.md` 写了怎么建、README 要有哪些章节）。

- 设计系统的 README 吸收 brief 和标杆卡的结论：内容与语气、视觉基础（层级、颜色含义、留白、材质、动效、触控与可访问性）、关键页面的层级、具名反面模式、给写代码的 agent 的规则。
- token 名字要和代码里使用的变量名一致。
- 设计系统的预览除了零件（颜色、字号、组件），还要有至少一张**真实场景的整屏预览**：只看零件判断不了效果，用户看到的是整屏。
- 渲染预览并在两个主题下看一遍，对比度达标后再发布。主题默认跟随系统，固定主题的特例屏在 README 里点名。
- 和别的产品共用入口时，基础 token 继承家族的那一份，导航和偏好记忆按约定写进 `<设计目录>/shell.json`（`references/family.md`）。
- 网页先上、App 后上时，README 写好每个组件到原生的对应（`references/app.md`「网页先行、App 后上」）。

把设计系统的链接写进 `<设计目录>/design-system.md`。

## 第 3.5 步：高保真交互稿先行（新界面或大改时必做）

**先在 Design 画布上把界面做到高保真、可点击，评审通过后再写代码。** 直接在代码里调样式，成本高、看不到全貌，还容易停在「能用但粗糙」。

0. **先交「假设 + 依据 + 占位」**，方向没定的新界面同一问题给 2–3 个版本并排放（`references/craft.md` §2）。要画哪些状态，从需求追踪表来，不凭印象：`coverage.py` 会列出还没画的功能。
1. 每个关键界面一张 390×844 的画板（网页用 1440 宽、`expand: "fill"` 的流式页面），覆盖关键状态：默认、完成的那一刻、第一次使用、空状态、出错。平台不止一个时（App 和网页），先定好各自的角色（例：App 负责「做」，网页负责「看」），两端都出稿。
2. 画板之间用链接串成流程，状态用 `data-props` 开关切换，让用户能点一遍。
3. 安装设计系统（画布的 `designSystems` 记录和 `project/ds/<folder>/tokens.json`），样式只引用 token；稿子里需要设计系统没有的值时，先补进设计系统。
3.6 **生成前清单**：每块画板交出前按 `references/preflight.md` 对一遍（首屏、交互与状态、外壳与主题、版式与视口、语言、颜色与材质、内容与 Agent 可用、证据）。
4. 每改一轮，先跑只读验证：`python scripts/verify_canvas.py <画板目录> --out <设计目录>/reviews/<日期-主题> --themes light,dark,pseudo`，修到 `done` 再给人看。**先核对报告里每块画板「查的视口」，再信结论**。查哪些项、参数、哪些证据要用 `capture_motion.py`、`render_dc.py` 另截，项目自己的阈值写进 `<设计目录>/design-bar.json`，命令不带参数也生效。见 `references/checks.md`。
5. 画板标题和生成脚本里不要手写「N 个场景」这类计数，会过时；需要时由脚本算。
5.5 卡片、播放条、工具栏、菜单、浮层要做「液态玻璃」时，先读 `references/liquid-glass.md`：先盘点哪些表面压在图片、视频、动效上（平涂底色上不用玻璃），材质做进 token（`assets/liquid-glass.css`），边缘透镜和按背景自适应用 `scripts/liquid-glass.js`；`verify_canvas.py` 会报「玻璃压在平涂底色上」。
5.6 一批画板分给几个 Agent 并行画时，按 `references/production.md`：小批、先探活、随写随存、`watch_workers.py` 盯进度、每块交回就提交。
6. 进入第 5 步的评审循环（同样必须独立评审），达标后再实现。实现时以画布为准，代码截图和画板并排对照。

## 第 4 步：同步进仓库

1. 用 Artifact 工具读出设计系统的 `project/tokens.json`，存到本地。
2. 生成代码用的 token：

   ```bash
   python <本技能目录>/scripts/sync_tokens.py tokens.json --out <tokens.css 位置> --source <设计系统链接>
   ```

3. 更新 `<设计目录>/design-system.md` 的同步时间。之后提交前可以用 `--check` 确认代码和设计系统一致。

代码里不手改 tokens.css。需要新 token 时，先改设计系统，再同步。

## 第 5 步：实现、检查、评审

**实现**：先读设计系统 README 和 tokens.css；新功能先在 `<设计目录>/features/` 写一份功能简报（模板在里面）。样式只引用 token。

**渲染**：项目有界面测试框架或组件预览时优先用它（模拟数据、离线、多场景）；没有再用开发服务器。登录后的页面用测试账号或模拟数据。

**每一轮**：

0. 画板先过 `verify_canvas.py`（上面第 3.5 步第 4 条）；需求文档有更新时，再跑 `coverage.py`（还有哪些功能没画）和 `stale_terms.py`（哪里还在用旧说法）。
1. `python scripts/check_page.py <页面> --out <设计目录>/reviews/<日期-主题> --dark`：多个宽度截图并做机械检查（项目见 `references/checks.md`）。
1.5 对外的页面有了能访问的构建或预览以后：`python scripts/check_agent_ready.py <站点地址或构建目录> --out <同一目录>`，必须项修到都过（`references/agent-ready.md`）。
2. `python scripts/lint_tokens.py <源码目录> --tokens <tokens.css>`：写死的颜色和数值、Tailwind 任意值、静态内联样式、`!important`、未定义的 token。传 CSS 变量和数据驱动的内联值不算问题。
2.2 `python scripts/check_shell.py <源码目录> --config <设计目录>/shell.json`：主题跟随系统、根元素写死主题、偏好记忆、家族导航约定。
2.5 **去模板味**：按 `unslop` 的信号清单审计（项目里有 unslop 技能时用它的 `references/signs.md`），判断重度、轻度还是没有；要改时按九遍顺序（间距 → 颜色 → 图标 → 文案 → 字体 → 版式 → 细节 → 视觉 → 动效）；最后做模板测试：把产品名换掉，这屏还成立吗（`references/craft.md` §1、§3）。
3. **独立评审，不自评。** 交给一个没看过制作过程的评审者（子代理），只给它：截图、brief、标杆卡、`references/rubric.md`、`references/anti-patterns.md`，以及上一轮的问题清单（要它逐条核对是否真的解决）。要求它对照 1–2 个顶级参照（标杆卡里的作品）指出最大差距，每个分数附截图证据。自己打的分不算通过：制作者会不自觉地宽松。会话不能开子代理时，用户就是评审者：把截图和打分理由交给用户，不自称达标。
4. 按「影响 × 修复成本」排序，每轮修前 3 项，修完回看已达标项。

**停止**：标杆原则都 ≥ 4 分且检查全部通过；或一轮没有提升；或已经 3 轮。不要以「找不到任何改进」为终点。

**定稿**（第一版、大版本）：在上面之外过「体验与美学」门槛：独立评审填 `<设计目录>/scorecard.md`，`python scripts/gate.py <设计目录>/scorecard.md` 过了才请负责人合并。定稿期间评审只按出口表判阻塞，表外的意见记进「上线后再看」（`references/award-bar.md` 第 3、4 节）。

**代码卫生**：复用已有组件；探索用的临时代码、废弃变体、未使用的样式在交付前删掉；改动范围与需求一致。

## 第 6 步：沉淀与交付

- **每条被接受的意见先归因，再决定改哪里**：
  1. 设计判断（这个产品该怎么样）→ 设计系统 README，数值改 `tokens.json` 再同步；
  2. 能机检的 → 检查脚本加一项，`selftest.py` 加一例；参数写错要报错，不静默；
  3. **制作方法的缺口（这个错为什么第一次就会犯）→ 改技能自己的步骤、清单或参考**（本技能的「生成前清单」、项目的版式技能），过时的句子同一轮删掉。只改目标文档、不改方法，下一次生成还会犯。
  同一类意见出现两次以上必须落到 2 或 3。每次在 `<设计目录>/decisions.md` 记一条。
  - 规则先定位再落笔：它是总纲（`ux-canon.md`）、标尺（`rubric.md`、`award-bar.md`）、做法（`preflight.md` 和各参考）还是检查（脚本）？先找同类的已有条目，合并、升级或改写，确实没有才新增。
  - 跨项目都错的说法记进技能的 `assets/canon-glossary.md`，只属于本项目的记进项目的 `glossary.md`。
  - 项目里的技能副本被改过时，改动先回到技能仓库，再用 `init_project.py --update-skill` 发回各项目；不在副本上各改各的。
- 用户提出修改意见时，按「决策原则」第 3 条处理：找出背后的原则，改完所有同类位置，写回设计系统，在交付里列出「顺带一起改的」。
- 交付：成品、改前改后截图对比、各轮分数、这次自己做的体验决定及理由、设计系统与 token 的本轮变更。只有属于「必须问用户」的事项才留给用户拍板。

## 需求变更时（产品决定影响界面）

1. **列出界面影响**：这个决定动到哪些画板和状态、设计系统哪几条规则、哪些文案和验收。
2. **同一轮改完**：设计系统 → 画板 → 需求文档的验收和交互描述，三处一起改，记一条 `decisions.md`。
3. **记进词汇表**：在 `<设计目录>/glossary.md` 加一行「废弃说法 | 现在的说法 | 依据」。
4. **扫一遍**：`python scripts/stale_terms.py --glossary <设计目录>/glossary.md <文档目录> <画板生成脚本> <源码目录>` 找旧说法；`python scripts/coverage.py --prd <需求文档> --canvas <画板目录> --map <设计目录>/coverage.md --batch '<当前批次>'` 找还没着落的功能（画了就在画板或生成脚本里写上功能编号，没有界面的在覆盖表写明理由）。它按功能编号算，看不出「功能里的一部分没画」，评审时还要对照功能描述人看一遍；内容模型的字段用 `--data`（`references/checks.md`）。
5. 交付时列出「顺带一起改的」。

## 打磨已有页面、全面检查已有设计

照 `references/audit.md`：渲染全部画板和状态 → 机械检查和覆盖 → 自己先写第一印象 → 两位互相看不到、侧重不同的独立评审 → 裁决成一份简报（保留、修补、重做）→ 先做外壳和设计系统、再并行做页面 → 复评。只改一两页时用它的「小范围」一节。打算继续迭代时，从现有页面反向整理出设计系统（第 3 步）。

App 或移动端交互，另读 `references/app.md`。

## 冲突时的优先级

以 `references/ux-canon.md` 第 3 节为准（安全、诚实和保真 → 无障碍底线 → 人掌控 → 完成任务 → 看得懂 → 设计语言一致 → 好看和惊喜）。体验层面的取舍按这个顺序自己定，写进 `decisions.md`；涉及产品意图或难以撤回的取舍，把选项和代价交给用户。
