# 已有设计的全面检查

什么时候用：需求变了一大块、要整体提升一档、接手别人或 AI 生成的设计、上线前的关口。只改一两页的，用最后的「小范围」。

和 SKILL.md 其余部分的关系：第 5 步的评审循环针对一轮改动；这里针对「整套设计现在到底怎么样」，产出是一份裁决过的简报，简报再进第 3.5 步和第 5 步去做。

## 步骤

1. **取回并渲染全部画板和状态。** 画板、共享样式表、`canvas.json`、设计系统的 README 和 `tokens.json` 都取到本地。每块画板截：基准视口整页、深色、另一种语言、最窄的视口、每个关键状态（`render_dc.py`）；动效截四帧（`capture_motion.py`，见 `checks.md`）。截图放一个目录，后面三方都用它。
2. **跑机械检查和覆盖。** `verify_canvas.py`（先核对报告里「查的视口」）、`coverage.py`、`stale_terms.py`。结果是评审的输入，不是结论：机械检查报 0 只说明它会查的那些项没问题。
3. **制作方自己先看一遍，写下第一印象。** 一句话，诚实；再列出自己已经知道的问题。写在派评审之前，之后不改：它用来对照评审，看自己漏看的是哪一类（漏看的类别回头补进生成前清单）。
4. **派两位互相看不到的独立评审，侧重不同。** 都没看过制作过程；各自只拿到材料和自己的任务说明，看不到对方的任务和结论；都只读、不改文件；能自己渲染。一位看得再细也会偏向一个视角，两份报告的交集是确定要改的，各自独有的发现正是分开派的价值。模板见下。
5. **主会话裁决成一份简报。** 评审之间、评审和需求之间的取舍在这里定，制作方拿到的是决定，不是两份意见。简报的结构：
   - 结论：保留什么、修补什么、重做什么（各一句理由）。
   - 全站共用的决定：栅格和内容左边缘、字号阶梯、导航和页脚、点按区域、深色主题、叫法、响应式的做法。每条写成能照做的规则。
   - 每块画板的决定：保留、要改的、要重做成什么样。
   - 设计系统要加、要改、要删的。
   - **和需求或规范冲突的地方单列**：评审的建议和已定的需求、质量规则冲突时，写明这次按哪边做，另一边由谁改，不让制作方自己选。
   - 评审指出但这次不做的，写理由。
   - 交付和检查：工作目录、要跑的命令、每块至少看哪些截图。
6. **先做共用外壳和设计系统，再并行做页面。** 外壳（导航、页脚、容器、共享样式、文案字典、内容数据）只有一份，先定稿；页面分支只引用，不各抄一份。
7. **复评。** 把上一轮的问题清单交回评审逐条核对，再按 `rubric.md` 打分。停止条件同第 5 步。

## 两份任务说明的模板

共同的开头（两份都有）：

```
你是独立评审，没参与制作。只读，不改任何文件，不发布。
材料：<截图目录>、<画板目录>、<需求文档>、<设计系统 README 和 tokens>、<标杆卡>、
<rubric.md>、<anti-patterns.md>、<机械检查的报告>、<已知缺口清单：这些不用重复>。
可以自己渲染（render_dc.py、capture_motion.py）。每个结论附证据：哪张图、哪个位置，或一个量出的数。
最后分开列三节：「规则缺口」（现有规则判不了、建议补的）、「没验证的」、「其他」。
报告写到 <路径>。
```

**评审 A：视觉和完成度**

```
侧重：这套设计离「拿得出手」差什么。
1. 第一印象：一句话，再列差得最远的三件事。
2. 对照需求里的愿景和主线：做到了什么，没表达出来的是什么。
3. 逐块画板：保留 / 要优化 / 值得重做。说重做的，写出重做成什么样、为什么比改更好。
4. 设计系统：该改、该加、该删的（栅格、字号阶梯、颜色在两种主题下、组件规则、和需求不一致的残留）。
5. 按标杆卡的原则逐条打分，列出不过的规则和证据；底线逐条判过或不过。
6. 具名反面模式和模板味信号，各在哪。
7. 按「影响 × 修复成本」排出前 8 项。
```

**评审 B：用**

```
侧重：真的来用的人顺不顺。
1. 扮成每一类用户走主线（<用户类型和各自的主线>）：每一步看到什么、想点什么、在哪犹豫、读了多少字才懂。
2. 5 秒测试：只看首屏，能说出什么、说不出什么（是什么、给谁、下一步、谁做的）。
3. 信息层级和阅读节奏：遮住文字看形状，每个区一个重点吗。
4. 内容和文案：每种语言分别看；按钮文字是不是点下去的结果；大字外行读不读得懂。
5. 手机和平板：现状，以及每个区块具体怎么排。
6. 无障碍和可用性底线：量对比度、最小字号、点按区域、键盘和焦点、不靠悬停、减弱动态效果。
7. 设计系统里导致这些问题的规则，各建议怎么改。
8. 重做什么、重做成什么样；按「影响 × 成本」排出前 8 项。
```

## 重做还是修补

重做 = 这一块的版式或内容结构从头来，保留设计语言。满足下面任一条就重做，否则修补：

- **问题在结构上**：信息顺序、版式类型、主操作是什么。逐条修完，结构性的那条还在。
- **两位评审独立指向同一块**，而且说的是同一类问题。
- **需求变了这一块的目的**（对象、核心任务、内容模型），不只是加减一个元素。
- **修补清单超过这一块元素数的一半**，或者修补之间互相牵动（改一处，另外三处要跟着动）。
- **换名测试不过**：换个产品名这一块照样成立（`craft.md` §1）。修细节改变不了这一点。

不重做的情况：问题是局部的、可数的（对比度、间距、点按区域、文案）；这一块是全站完成度最高的；重做会推翻用户确认过的方向。推翻确认过的方向属于「必须问用户」，不在这里自己定。

每一条「重做」在简报里都写明保留什么：设计语言、已经确认的方向、评审说好的部分。

## 小范围：只打磨一两页

先做第 1 步里会影响方向的几项确认（SKILL.md 第 1 步），再输出诊断，然后动手：

- 第一印象（一句话，诚实）；
- 与标杆最大的 3 个差距；
- 识别到的具名反面模式；
- 检查脚本发现的问题；
- 修改顺序，以及哪些大改动（换字体、换配色、改结构）要先确认。

评审照第 5 步，一位独立评审即可。
