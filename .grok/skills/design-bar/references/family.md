# 外壳、主题和产品家族

> 什么时候读：建立设计系统时（第 3 步）、画导航和设置时（第 3.5 步）、产品和别的产品共用域名、入口、账号或设计系统时，以及改动会碰到另一边的东西时。
> 为什么有它：主题和导航是用户在每一屏都碰到的「外壳」。一边写错（例如设计系统里写了浅色固定、不跟系统走），或者约定只写在一个仓库里、没落到另一个，用户就会觉得「这像另一个网站」，上线检查也会卡住。

## 1. 主题：默认跟随系统

- 浅色、深色默认跟随系统（CSS 的 `prefers-color-scheme`）；用户可以手动选「自动、浅、深」三档，选择存在一处（一个存储键），刷新、跨页、跨产品都还在。
- 固定某一种主题只给少数特例屏，例如训练中、播放中整屏深色。特例在设计系统 README 里点名，写进 `shell.json` 的 `theme.fixedAllow`（源码路径的正则）；特例以外，根元素不写死 `data-theme`，代码不把主题无条件设成浅或深。
- 深色单独设计，不是反色（`anti-patterns.md`「反色深色模式」）。

## 2. 产品家族：约定，不共享代码

几个产品共用一个域名或入口（例：主站和它下面的子产品）时，用户只需要认得出「还在这一家」、知道「怎么回去」。做到这一点靠三条约定，不需要把导航打成共享代码包：共享包要发版本、两边同步，总有一边落后。

1. **站标回家族首页**：子产品导航左上角的站标链到家族首页（各语言各自的首页）。
2. **同级产品的链接**：导航里有同级产品的链接，地址按约定写，当前所在的高亮，并用 `aria-current` 告诉读屏和 Agent，不只靠颜色。
3. **偏好共用**：语言和外观的选择读写同一组存储键，取值一致（例：语言 `zh` / `en`，外观 `auto` / `light` / `dark`）。

另外两件：

- **设计 token 同一来源。** 子产品的设计系统继承家族的基础 token（颜色角色、字号阶梯、玻璃参数），只在产品自己的层加东西；两边各改各的基础 token 迟早不一致。
- **改动通知另一边。** 改到共享的东西（导航约定、登录、入口落地页、设计系统基础 token、`shell.json`）时，同一轮通知另一边，并在两边的 `decisions.md` 各记一条。旧做法改掉后，把旧说法记进两边的词汇表（例：「共享外壳包」）。

## 3. 写成 `shell.json`

约定写在 `<设计目录>/shell.json`，两边各放一份、内容一致（家族首页那边是源头）。`init_project.py` 会放一份只含主题的模板。

```json
{
  "theme": {
    "storageKey": "vc-theme",
    "values": ["auto", "light", "dark"],
    "fixedAllow": ["src/app/train/"]
  },
  "family": {
    "home": "/",
    "links": ["/body", "/mind", "/build"],
    "langKey": "vc-lang",
    "langValues": ["zh", "en"]
  }
}
```

- 不属于家族的产品，`family` 写 `null`。
- 没有手动切换主题的产品，`storageKey` 写 `null`。

## 4. 怎么查

- **画板**：导航在浅色、深色、每种语言下都有一块画板，当前所在的高亮画出来；子产品的覆盖表（`coverage.md`）里要有这一行。
- **源码**：`python <本技能目录>/scripts/check_shell.py <源码目录> --config <设计目录>/shell.json --out <报告目录>`。查：有深色主题却没写跟系统切换、根元素写死主题（特例目录除外）、约定的存储键和取值没出现、家族首页和同级链接没出现、没有 `aria-current`。它读源码文本，判不了运行时的行为，所以：
- **上线前**：打开子产品的入口页（每种语言），逐条点一遍三条约定，切换外观和语言后跳到另一边看是否还在。主站或家族首页的上线测试应该包含这一步，不过不切域名。
- **文档**：`stale_terms.py` 自带一份通用词汇表（`assets/canon-glossary.md`），设计文档里写了主题不跟系统的说法会命中。
