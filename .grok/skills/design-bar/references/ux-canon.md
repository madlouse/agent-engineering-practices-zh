# 体验原则总纲：给人用的界面（GUI）、人和 Agent 一起做事（AUI）、Agent 来用的网站（AX）

> 什么时候读：开工前定方向（第 1 步）、生成前清单（第 3.6 步）、评审和打磨（第 5 步），以及任何人提出新的体验原则时。
> 这是跨产品的通用版本。项目把它落成自己的规则表（例如 Velicoach 的 `docs/standards/quality-terms.md`），只写项目的数值和对标，不重抄原则。
> 来源：苹果 HIG（2026-06-08 重新发布的设计原则，以及 Generative AI、Machine learning 两页）、迪士尼 Imagineering 和乐园运营、Vercel 的 Web Interface Guidelines 和 design.md、Shopify Polaris、Anthropic 和 OpenAI 公开的 Agent 设计、微软 Human-AI Interaction 18 条、Google PAIR、NN/g。逐条出处和批判见 Velicoach 仓库 `docs/uiue/research/2026-11-06-ux-canon/`。

## 0. 一句话

**让人以最少的负担，在自己掌控、看得懂、信得过的前提下达成目标；Agent 也是用户，和人读同一份结构。**

「最少的负担」不是「最少的点按」。负担是：要读的字、要做的决定、要记住的东西、等待的焦虑、出错的代价。

## 1. 九条原则

每条写：一句话、为什么、怎么判（能写成检查的标 ✓）、主要出处。

| # | 原则 | 为什么 | 怎么判 | 主要出处 |
|---|---|---|---|---|
| 1 | **目的先行，内容优先**（第一屏就是论点或工具，不是刊头加铺垫）：每屏先回答「这是给谁的、能做什么、下一步是什么」；装饰让位于内容 | 人来是为了做事；苹果说 Simplicity 不是极简，而是每个元素都配得上它的位置 | 首屏有受众词、一个主操作；遮住装饰，任务照样能完成；每节回答一个新问题，每个论断只有一个证据位置，不重复摘要 | HIG Purpose、Simplicity；迪士尼 story first、wienie；Vercel design.md |
| 2 | **沿用熟悉的约定，看得懂就会用** | 学新约定是负担；熟悉让人一来就知道怎么用 | 站标回首页、放大镜是搜索、带下划线的是链接、当前位置高亮 ✓；只用图标的按钮限于通行图标；首屏要读的说明有字数上限 ✓ | HIG Familiarity；Krug《Don't Make Me Think》；NN/g 图标研究 |
| 3 | **去掉不承载意图的步骤，保留承载意图的步骤** | 「零步」是神话：苹果给 Apple Pay 加了一步双击确认付款，迪士尼把规划挪到入园前。真正要省的是重复、中间页、无意义的选择，不是确认意图 | 步数表里每一步标「意图步」或「可删步」；可删步超预算就改设计；意图步（同意、付款、不可逆、对外发送）不计入预算，也不许省掉 | HIG Agency；Apple Pay；迪士尼 Lightning Lane；Polaris「用摩擦突出重要决定」 |
| 4 | **即时回应，设计等待** | 「快」分两层：回应（按下就有反馈）和完成（拿到结果）。生成式任务做不到 1 秒完成，但能 0.1 秒回应、说清在做什么 | 按下 0.1 秒内有反馈；非生成类操作完成 P95 ≤ 1 秒；转圈延迟约 150–300ms 才出现、出现后至少显示约 300–500ms（防闪）；超过 1 秒写「动词 + 对象」的进度，不写「加载中」✓；超过 10 秒的允许离开，完成后通知 | NN/g 响应时间三界限；WWDC18 Designing Fluid Interfaces；Vercel；HIG Generative AI；Maister 等待心理学 |
| 5 | **人掌控：能撤销就不确认，撤不回的才确认** | 每步都确认会让人乱点同意（Claude Code 的确认请求 93% 被直接同意）；一步不确认又会闯祸 | 每个动作标「可撤销 / 需确认」✓；可撤销的做完给撤销；需确认的写清后果；导引流程可以跳过、能退出 | HIG Agency、Generative AI；Anthropic 自主度实测；Vercel；Polaris |
| 6 | **可信：说清是什么、从哪来、多有把握** | 生成内容看起来权威，人不核对；暗中个性化让人不知道结果为什么变 | AI 生成或合成的内容有可见标识 ✓；说法可以简化、论断不能简化，改变含义的限定语一个不丢；事实附可点出处；数字和安全判断由代码给出，不由模型给出 ✓；把握不高时不主动推，把握用能照着做的话说，不显示百分比；记住了什么能看、能删 | HIG Responsibility、Generative AI、Machine learning；微软 G1、G2、G11、G12–G18；PAIR；Anthropic 宪法 |
| 7 | **一站、连续：不离开、不重来、不丢状态** | 跳出去、再登录、刷新后从头来，都是在重复劳动 | 完成旅程不离开本站、不再登录；语言、筛选、展开、搜索词、输入了一半的内容在刷新、后退、换设备后都还在；主要状态写进地址 ✓ | HIG Flexibility「保留上下文」；迪士尼 MagicBand 串起旅程；Vercel；W3C Cool URIs |
| 8 | **人和 Agent 读同一份结构** | 浏览器 Agent 先读无障碍树，看不清才截图；对人无障碍，对 Agent 就可用 | 可点元素是原生控件、有可读名称 ✓；展开的选项不靠悬停存在 ✓；正文不执行脚本也读得到 ✓；机器可读件（结构化数据、站点地图、RSS、llms.txt）都由内容数据生成 ✓；读内容和订阅不用验证码；后果大的动作在站点一侧确认 | web.dev；Google AI 搜索指南；Claude 浏览器工具文档；Netlify AX；llmstxt.org |
| 9 | **装饰要证明自己有用** | 惊喜来自好用，不来自装饰；装饰的成本（性能、可读性、维护）常被低估 | 动效先过必要性检查：说清因果，或者一处刻意的签名；动画进行中输入立刻生效（可打断）✓；材质（玻璃、透镜）先答「透过它看到的东西对人有没有用」，并有性能预算 ✓；品牌表达不挡任务 | HIG Delight「Don't mistake delight for decoration」；Polaris；Vercel 动效规则；OpenAI 应用规范 |

## 2. 冲突时的先后

原则会打架。迪士尼的 Four Keys 给冲突排了先后（安全在礼貌之前），苹果把 Responsibility 放在 Delight 之前。照这个思路，冲突时按下面的顺序让步：

1. **安全、诚实和保真**（原则 5 的撤不回要确认、原则 6；给定的事实、数字、单位、限定语一个不改）
2. **人掌控**（原则 5、7）
3. **完成任务**（原则 1、3、4）
4. **看得懂**（原则 2）
5. **好看和惊喜**（原则 9）

例子：
- 省一步和确认付款冲突，保留确认。
- 玻璃好看和文字对比度冲突，换实色。
- 首屏少读字和说清 AI 生成冲突，保留标识。

## 3. 人和 Agent 一起做事（AUI）的规则

产品里有 Agent 替人做事时（例如 Veli 的威利提前排好训练），加这几条：

| 规则 | 怎么查 |
|---|---|
| 先说清能做什么、常在哪出错；空状态给 2–4 个能直接点的用例 | 设计评审 |
| 人说结果，Agent 给可编辑的计划或预览；常用约束做成控件，不靠打字 | 走一遍 |
| 每个主动动作在配置里声明自主等级和是否可逆；不可逆或对外有后果的必须先确认 | 对动作配置做 lint ✓ |
| Agent 执行时，停止按钮一直可见，按下 1 秒内生效，已完成的部分保留 | 端到端 ✓ |
| 有一条活动记录：Agent 替人做了什么、为什么，每条能撤销 | 端到端 ✓ |
| 跨会话的任务把步骤、当前步、下一步存在服务端，中断后从断点继续 | 端到端 ✓ |
| 生成结果旁有编辑、撤销、重试中的至少两项；人的修正立刻生效并被记住 | 组件测试 ✓ |
| 主动提醒受打扰预算约束，不在人正在做的事中途打断 | 规则引擎单测 ✓ |
| 生成式界面只用组件目录里的类型拼，props 过 schema 校验，不渲染模型给的任意 HTML | 单测 ✓ |
| Agent 主动提问只问偏好和意图，给可点的选项 | 抽查 |
| 敏感输入（密码、付款）由人自己输入，Agent 不看、不存 | 走一遍 |

## 3.5 给 Agent 用的设计说明怎么写（design.md 式）

设计规范要让 Agent 读了就做对，不只是让人看懂。做法来自 Vercel 的 [design.md](https://vercel.com/design.md) 和[配套博客](https://vercel.com/blog/how-our-agents-build-on-brand-pages-with-design-md)，本技能和项目的版式技能都按它写：

1. **写成技能**：说清「什么时候用」和「你是谁」，再写先后顺序。
2. **判断写成文字，机械交给接口和检查**：Agent 只用公开的 token 和类名，不读样式表的实现，不自己发明类名或 token（`lint_tokens.py` 查）；找不到合适的就用语义 HTML 加页面自己的钩子。
3. **冲突时的先后写在最前面**（本文第 2 节）。
4. **只在关键处提问**：未知会改变事实含义、法律或安全说法、隐私、公式、人群或行动号召时，问一组问题；否则标出缺口，继续做。
5. **点名反模式**：模型认得出有名字的模式，笼统的「别有模板味」不管用。清单见 `anti-patterns.md`。
6. **四遍**：框定读者要做的事 → 选构图（先说出这一品类显而易见的默认版式，材料配不上就不用；私下比较两种结构不同的方案）→ 按视觉系统做 → 自己渲染、检查、改到没有已知问题。交付成品，不交分数和过程日记。
7. **同一条意见出现第二次，就同时写进规范和一条确定性检查**；只在一个模型上出现的问题先不写，等它在多个模型上重复再写。

## 4. 已经被推翻或要警惕的说法

| 说法 | 结论 | 理由 |
|---|---|---|
| 步数越少越好、「零步」 | 推翻 | 见原则 3 |
| 「一秒」对所有操作 | 改成两层 | 见原则 4 |
| 「三次点击规则」 | 推翻 | NN/g 的数据不支持；点按次数不等于负担 |
| 每步都让人确认才安全 | 推翻 | 确认疲劳；按后果分级 |
| 沉浸感（迪士尼乐园式） | 工具类产品里要警惕 | 乐园靠藏起外部世界、操纵尺度感；搬到工具上就成了藏系统状态、暗黑模式 |
| 玻璃越透越像苹果 | 要警惕 | 苹果的 Clear 玻璃要同时满足三个条件才用，iOS 26.1 补了 Tinted 开关；阅读类产品默认用厚一档的玻璃，「看得到背后」只是允许用玻璃的门槛，不是目标 |
| 悬停 80ms 展开是标准 | 没有出处 | 是自定的数，要用真实鼠标轨迹测误触 |
| llms.txt、WebMCP 能带来流量 | 不当增长手段 | llms.txt 是提案，Google 搜索不读；WebMCP 是社区组草案、只在源试用里；便宜的顺手做，不为它们改架构 |
| 熟练用户的工具（Polaris 后台）只用图标 | 只适合每天用的工具 | 第一次来的访客要通行图标加文字 |
| 不要玻璃、默认静止、不要庆祝（Vercel design.md） | 只适合它的场景 | 那是给做决定的高管看的报告页的口味；可以借的是背后的检验「装饰要证明自己有用」，不是禁令 |

## 5. 怎么用

1. **开工前**：读第 0–2 节；在功能简报里写清这个功能里哪一步是「意图步」、哪个动作撤不回、有没有 Agent 在替人做事。
2. **生成前清单**：第 1 节标 ✓ 的规则，项目都应该有对应的检查（`verify_canvas.py`、`check_page.py`、lint、端到端测试）。还没有的，先写成检查再出稿。
3. **评审**：评审按项目的规则表打分，有冲突时按第 2 节裁决。
4. **复核**：每次有人提出新的体验原则，或者对标产品发布了新版规范，先在这里判一次。要判的是：它和哪条原则重合、要合并还是升级、证据够不够、在什么场景下不成立。结论写回本文件第 4 节，再改项目的规则表。每条原则在新证据出现时都可以被推翻。
