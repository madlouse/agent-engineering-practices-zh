# Velicoach 内容规范

Velicoach（velicoach.com）是「AGI 路上的陪练」：01 站稳（力量训练，产品是 Veli）、02 看清（AI 发展史与人机协作）、03 动手（和 agent 一起做出能用的东西）。本技能规定所有对外内容怎么写、怎么审、怎么定期校准。页面怎么排版见 `velicoach-layout` 技能。

技术内容的中文排版沿用冯大辉的《中文技术文档写作风格指南》（Fenng/Tech-Doc-Style-Chinese，MIT 许可），本技能按 Velicoach 的读者和品牌做了取舍和补充。

## 1. 先确定模式

| 模式 | 什么时候 | 产出 |
| --- | --- | --- |
| 撰写 | 从素材写新内容 | 中英两版成稿 |
| 改写 | 结构或语气要大改 | 成稿，加一段改了什么、为什么 |
| 校对 | 只修错字、标点、留白、术语、大小写 | 修改后的稿件，不动结构和观点 |
| 审阅 | 只给意见，不改稿 | 按第 8 节格式的审阅报告 |
| 校准 | 定期回看已发布内容和规范本身 | 校准记录，以及对规范、术语表的修改 |

用户没说模式时，按请求判断；拿不准时按「审阅」处理，不擅自改稿。

## 2. 规则优先级

冲突时按这个顺序取舍，前面的优先：

1. **事实**：原文、研究、产品能力、日期、数字。不确定的标「待核实」交回给人，不自行补全；这类标记永远不能出现在发布稿里。
2. **项目约定**：Velicoach PRD 的术语表和内容框架、Velicoach 设计系统 README 的「内容与语气」、健康内容以 Veli PRD 和知识库为准。
3. **技术准确**：概念、代码、命令、API 名称、版本号。
4. **结构与语气**：本技能第 3 至 5 节。
5. **排版**：第 6 节。

「好懂」「可信」「专业」「有深度」这些词的意思以 `docs/standards/quality-terms.md` 为准（规则 C、T）；审核时按条目编号说话。

跨产品的内容底线和生态术语在同级目录的 velicoach-mono/standards/content.md、velicoach-mono/glossary.md；写到 Veli、种星词或生态本身时先对一遍，主站内的写法以本技能为准。

排版规则只作用于可见正文，不改代码、路径、字段名、URL、命令、配置项、引用原文和产品官方写法。

## 3. 事实来源

- Velicoach 主站 PRD（在线文档是唯一来源，仓库快照在 `docs/prd/velicoach.md`）：内容框架、每种内容的必填字段、术语表、授权规则。术语以 `docs/GLOSSARY.md` 为准。
- 产品负责人的原话在 `docs/requirements/timeline.md`，理解和裁决在 `docs/requirements/trace.md`；拿不准一句话的本意时回去读原话。
- Velicoach 设计系统 README（副本在 `docs/uiue/system/README.md`）：品牌语气、三站的气质。
- 健康和训练内容：Veli PRD、Veli 知识库。训练指导都在 Veli 里，由持证教练审核（Veli 的规矩）；主站的研究卡不经持证教练，按第 5 节「研究卡」把关。
- 翻译和讲解：以原文为唯一依据；原文没写的，不替作者补。

## 4. 共同的写法

**对外只放正式版。** 发布稿里没有占位符、过程说明、「示例」「待定」「即将上线」、写作者的自言自语。过程思考写进设计或过程文档。

**素材不等于成稿。** 用户口述和语音转写里的口头禅、重复、识别错误不进稿件（`AGENTS.project.md`「不能越过的线」第 1 条；`npm run check:voice`）。按整体目标判断一句话该不该存在：意思对、但说法是口语的，改写成书面语，用术语表的标准术语；意思和目标不符或明显是识别错误的，删掉，并在交付说明里列出删了什么；拿不准的名字列给产品负责人确认，不猜。新发现的转写错误加进术语表「口语和转写错误」。

**一句话一件事，先说结论。** 段落第一句就是这段的结论；中文导语每行不超过 32 个字。

**用行业通用的词，谨慎造词。** 按 `docs/GLOSSARY.md` 写：有通行中文译名的用中文（智能体、提示词工程、上下文工程），没有的保留英文并在第一次出现时带一句白话（Harness 工程、Loop 工程、Graph 工程）。表里没有的新名字，先查业界怎么叫，确实要新起就先加进术语表。不为变化而换同义词，同一概念全文一个叫法。

**具体，有出处。** 数字带单位；健康研究写明研究类型、样本量和年份，例如「Cochrane 系统综述，2019 · 59 项试验」；引用写明作者、标题、链接和日期。

**讲力量，不讲身材；不制造焦虑。** 写「每周 30–60 分钟力量训练」，不写「再不练就晚了」。研究卡只有三张：防摔、长寿、情绪，不放外形。不做医疗诊断，不给用药建议。

**专业但好懂。** 读者是聪明的外行。先讲这件事对读者有什么用，再讲原理；一个段落里新术语不超过两个；能用一个例子讲清的，不用三个形容词。

**少用空话。** 以下词只有在有明确定义、引用原文或属于正式术语时才用，否则写出实际动作：赋能、抓手、闭环、沉淀、对齐、对标、拉通、打通、协同、联动、洞察、赛道、心智、调性、战役、链路、势能、兜底、落盘、收口、透传。「场景、生态、体系、路径、复盘、梳理、输出」看语境，不机械替换。

**称呼。** 页面文案、订阅邮件、社交帖子可以用「你」；文章正文和技术说明优先用无主句或明确的角色（开发者、读者）。全站不用「您」「同学」「小伙伴」。

### 看清的技术品味

看清参考陈皓（酷壳、「左耳听风」）的技术品味：借他对技术的判断，不模仿他的文风，更不照搬他的网站。写看清的内容时，每条判断都要落到稿子里：

- **学方法，不只给答案。** 先讲原理，再讲用法；学习路径的每一步写清楚为什么学、学到什么程度、怎么检验自己学会了；每篇留一个读者能自己动手验证的练习。
- **没有捷径。** 不写「三天学会」「速成」；学习路径标出大概要花的时间。
- **先给地图，再给工具。** 讲清一件事在 AI 发展史上的位置，或在工程范式演进（提示词工程 → 上下文工程 → Harness 工程 → Loop 工程 → Graph 工程）里的位置，不写工具清单。
- **从做过的事出发，有观点。** 开头先给判断：值不值得学、适合谁、我们的结论；实践类写清楚代价和踩过的坑，敢写「不推荐」。
- **不追热点。** 新模型、新框架出来，等能说清它改变了什么再写；标题说清讲什么，不用问号和感叹号吊胃口。
- **让知识能被检索、引用、更新。** 每篇写明发布日期（本站发布这一篇的日期）、「适用于」（模型、版本）和最后核对日期，有原文日期（原作发表的日期）时也写；里程碑和学习路径步骤写最后核对日期（`docs/standards/quality-terms.md` T3）；改过的记进更新记录；每个小节有锚点；每个说法有出处。
- **知道多少说多少。** 没验证过的标明没验证过；不懂的不写；读者指出的错误公开改正。
- **克制。** 不用感叹号，不用「炸裂」「颠覆」「史诗级」，不用表情符号。

### 英文版

- 英文按英语读者重写，不逐句直译；中文里的对仗、四字格、排比不硬搬。
- 美式拼写；标题用 sentence case（只有首词和专有名词大写）；列表用 serial comma。
- 名词用术语表的英文：站名 Body、Mind、Build；Veli、Newsletter、Devlog 照写。
- 句子比中文更短，主动语态；不用 leverage、empower、unlock、seamless、delve、journey、game-changer 这类空泛词。
- 中英两版同时发布；英文页面里不出现中文正文和未翻译的界面文字。

## 5. 每种内容怎么写

必填字段以 PRD 第 5 节为准；下面是写法和验收。

| 内容 | 写法 | 验收 |
| --- | --- | --- |
| 研究卡片 | 三张：防摔、长寿、情绪。一句结论（数字写在句首），一个关键数字，研究类型、样本量、证据可信度、年份、出处；写法见表后「研究卡」 | 数字能在原文里找到；出处链到论文原文；措辞和研究类型相符（观察性研究不写因果）；`npm run check:research` 通过（站点票 #52 交付，交付前人工逐张核对） |
| 里程碑 | 年份、事件、一句话说路线怎么变了、为什么是转折；原始论文或文章；能动手学的课程和代码 | 一句话不超过 40 个字；原文链接可打开；站内有讲解时链接过去 |
| 学习路径步骤 | 序号、名称、来源、形式；为什么学、学到什么程度、怎么检验自己学会了、大概要花多久 | 每步都能说出前置步骤；检验方法是读者能自己做的事；链接指向作者的官方地址 |
| 文章（全文译文） | 只发官方中文、开放授权或已取得授权的文章；忠实原文，按第 6 节排版 | 原作者、原文链接、日期、授权说明齐全；保真检查通过 |
| 文章（讲解） | 未授权的文章只做讲解和摘要：先写一句话结论，再讲三到五个要点，引用原文不超过必要的几句 | 读者不读原文也能明白要点；明确标出哪里是原文观点、哪里是我们的理解 |
| 3 分钟视频 | 只给重点文章做（重点文章 = 同时收进 AI 发展史里程碑的文章）；其余文章不做，也不被视频卡住发布。5 个镜头、3 分钟左右；中文旁白晓晓、英文旁白 Andrew；脚本先过保真检查 | 字幕和文字稿齐全；每个镜头只讲一个点 |
| 开发日志 | 日期、项目、做了什么、和智能体怎么分工、下一步；写失败和返工，不只写成功 | 有一个读者能照着做的具体细节（命令、提示词、截图之一） |
| 订阅邮件 | 每周日一封：一读、一练、一个可以动手做的项目；开头一句话说本周主题。每期一份邮件文件，只用已发布的内容按固定模板拼成；「一练」不写训练动作，只放一句有出处的话和去 Veli 训练的入口；这周没有达标的新文章时，改放里程碑更新和开发日志 | 三项各有一个链接回站内，链到的内容都已发布；一屏读完；有退订链接；周五开了「订阅邮件第 N 期」的票（`docs/standards/pipeline.md` §5.1） |
| 页面文案 | 标题说结果，按钮写点了之后得到什么（「开始训练」「读最新文章」，不写「了解更多」）；登录后的入口用「继续」（v2，主站 v1 不读登录状态）；空状态说清下一步 | 中英两版长度差异能放进同一个版式；伪语言加长 35% 不截断 |
| 社交帖子 | 一条只讲一个点；第一行就是钩子；链接带渠道参数回到站内。Agent 只起草分发包，帖子由产品负责人自己发 | 不夸大、不标题党；平台字数限制内 |

### 研究卡

首页「为什么是现在」的三张健康研究卡：防摔、长寿、情绪。不放外形；研究卡只在首页，全站只有这一份数据。

1. **出处链到论文原文**：链接是论文的 DOI 或出版方页面，不链新闻稿、二手报道和机构的介绍页。出处表里摘录支撑结论的原句和查询日期。
2. **研究类型决定措辞**。数据里记研究类型，结论句的动词按类型选：

   | 研究类型 | 可以写 | 不写 |
   | --- | --- | --- |
   | 随机对照类：随机对照试验，汇总随机对照试验的系统综述或荟萃分析 | 「降低」「减少」「缓解」（英文 reduces、lowers、relieves） | 超出试验人群和结局的推广 |
   | 观察性：队列、病例对照、横断面研究，以及只汇总这类研究的系统综述 | 「有关」「相关」（英文 is associated with、is linked to） | 「降低」「减少」「预防」「导致」「能让」这类因果措辞（英文 reduces、prevents、causes） |

   一篇综述两类研究都有时，按卡片上那个数字出自哪一类判；拿不准按观察性写。

   **措辞还要看证据可信度，不只看研究类型**：可信度是「低」或「很低」时，结论带「可能」（英文 may），并把可信度写进句子；证据可信度只写一个词（高、中、低、很低），三张口径一致。**写清人群和干预**，不把研究没单独证明的事写进去：综述比的是各类运动项目，就不写成力量训练的效果，并注明只做抗阻练习的证据够不够。**大数字是外行读得懂的一个数**（百分比、人数这一类）：研究只给出效应量时不放大字，效应量照原样写进方法一行，由结论句说它是大是小，不自己换算成百分比；有大数字时结论句以这个数字开头，英文不超过 28 个词。三项按证据可信度从高到低排。版式见设计系统「研究卡」；`quality-terms.md` T8 里「效应量照原样当大字」一句和这里不一致，待主频道定（`docs/uiue/decisions.md` 2026-11-13）。
3. **检查脚本**：`npm run check:research` 按研究类型拦因果措辞，由站点票 #52 交付。交付前由冷审逐张人工核对第 1、2 条。
4. **首批由产品负责人看一次**：首批三张上线前，产品负责人本人在内容票 #9 里回复看过并留一句结论（什么算他的回复按 `pipeline.md` §6 的判法，别的账号的评论不算）；以后新增或改写研究卡，走内容票的一份冷审，不再等他。
5. **持证教练只审训练指导**，训练指导都在 Veli 里；研究卡不经持证教练。每页写明「威利不是医生」。

## 6. 中文排版（技术内容为主，全站通用）

**留白（盘古之白）。** 中文与英文、数字之间加一个半角空格：「使用 API 获取数据」「等待 3 秒」「版本 2.0」。中文与行内代码之间加空格：「运行 `npm install` 安装依赖」；行内代码紧挨中文标点时不加：「运行 `npm install`。」全角标点前后不加空格。不用连续空格或全角空格对齐。

**标点。**

- 中文正文用全角标点；引号用「」，嵌套用『』。
- 文章、书、课程名用《》；按钮、菜单、字段的显示名用「」；机器可读的字段名用行内代码。
- 中文括号用全角（），内侧不留空格；英文原文和代码里的括号保持原样。
- 省略号用「……」，破折号用「——」；不用三个英文句点或连字符代替。
- 并列词语用顿号；不连用感叹号；冒号后面必须真有解释或列举。
- 完整句子的列表项用句号结尾；短语列表不加句号；同一个列表保持一致。

**数字、单位、日期。**

- 数字和单位之间空一格：「10 GB」「200 ms」；百分号和角度紧贴数字：「50%」「90°」。
- 中文日期写「2026 年 11 月 3 日」；时间「15:30」；面向跨时区读者时写明时区。
- 范围在正文里写「3 至 5 天」，表格和界面里可以用「3–5」。
- 分清百分比和百分点；「翻了 1 倍」写成「变为原来的 2 倍」；「缩小 3 倍」写成「缩小到原来的 1/3」。修正说法时不补原文没有的数字。

**术语大小写。** 按官方写法：API、URL、JSON、HTTP、ID、AI、LLM、RAG、JavaScript、TypeScript、Python、Node.js、GitHub、PostgreSQL、gRPC、GraphQL、WebSocket、WebGPU、three.js、ChatGPT、OpenAI API。中文正文写「智能体」，第一次出现写「智能体（agent）」；产品名和引用原文保持原样。JS、Postgres、k8s、OAuth 看语境，正式正文写全称。

**常见错字。** 阈值（不是阀值）、部署、返回、回溯、作为、截至（到某个时间点）与截止（期限）、登录（系统）与登陆（月球）、认证（确认身份）与授权（授予权限）。

**源文件。** Markdown 一段一行，不在段落中间手动断行；代码块、表格、标题、引用块保留原有换行。代码块标明语言。标题最多三级。

**结构。** 技术文章的开头先回答三个问题：这篇讲什么、读者读完能做什么、需要什么前置知识。长文章（超过 2000 字）在开头放目录；每一节以结论句开头。操作步骤用有序列表，每步一个动作，写明预期结果。

## 7. 流程

一篇内容从立项到发布走这几步。内容由 agent 生产时，每一步都要留下可检查的证据。

1. **立项**：确定属于哪一站、哪条内容线、哪种内容类型；核对授权状态（只能讲解的，不做全文译文）。
2. **撰写**：按第 4 至 6 节写中文版，再按英文规则写英文版。
3. **保真**：译文和讲解逐段对照原文，检查有没有遗漏、曲解或添加。有 `article-fidelity` 技能时用它。
4. **中文风格与排版**：按第 6 节逐项过一遍。有 `article-zh-style` 技能时用它，两者冲突时以本技能为准。
5. **可读性**：按第 4 节检查结构和语气；页面文案再用 `unslop` 的文案部分过一遍，去掉 AI 味（空泛形容、三连排比、「不仅……更……」、每段都以总结收尾）。
6. **3 分钟视频**：只给重点文章做（同时收进 AI 发展史里程碑的文章）；用 `article-feynman` 生成脚本和旁白，脚本先过第 3 步。
7. **配图**：图表和插图要有文字说明和出处；用 `article-visual` 时，图的样式服从 Velicoach 设计系统。
8. **审核**：见第 8 节。
9. **发布前检查**：见第 9 节，全部通过才发布；中英两版一起发布。

## 8. 审核

审核分三层，后一层不替代前一层：

1. **自查**：写作者按第 9 节的检查表逐项打勾。
2. **冷审**：另开一个不带写作过程上下文的 agent，只给它原文、成稿和本技能，让它按审阅模式出报告。
3. **人审**：只留给三种内容，由产品负责人定稿：新开栏目或内容线的模块样稿、训练指导（都在 Veli 里，由持证教练审核）、涉及法律、付费和对外承诺的；全文中文版要向作者取得授权的，由产品负责人出面。每周的站上内容（文章、里程碑、开发日志）冷审通过就发布，产品负责人每周收一份摘要，事后可撤；订阅邮件发出前他可以取消（`docs/standards/pipeline.md` §5.1）。首批研究卡由产品负责人看一次（第 5 节「研究卡」）。质量先于节奏：没有达标的文章这周就不发。

问题分三级：

| 级别 | 含义 | 例子 | 处理 |
| --- | --- | --- | --- |
| 阻断 | 不改不能发布 | 事实错误、数字找不到出处、授权不明、医疗建议、出现占位符或过程性文字、英文页面出现中文正文 | 必须修复后重审 |
| 必改 | 影响理解或品牌一致 | 术语不一致、造词没解释、结论没有放在段首、黑话、制造焦虑 | 发布前修复 |
| 建议 | 排版和措辞的打磨 | 留白、标点、更短的说法 | 可以合并到下一次修订 |

审阅报告的格式：

```markdown
## 审阅：<标题>（<中文 / 英文>）

结论：可以发布 / 修改后发布 / 不能发布

| 级别 | 位置 | 问题 | 建议改法 |
| --- | --- | --- | --- |
| 阻断 | 第 2 节第 1 段 | 「提升 40%」原文为 40 个百分点 | 改为「提高 40 个百分点」 |

没有改动的地方：<为什么保留，例如引用原文>
```

## 9. 发布前检查表

- [ ] 事实、数字、日期都能在出处里找到；出处链接可打开。
- [ ] 作者、原文链接、日期、授权说明齐全（译文和讲解）。
- [ ] 没有占位符、「待核实」、过程说明、口头禅和转写错误。
- [ ] 术语与 PRD 术语表一致；新术语第一次出现时有一句解释（`docs/standards/quality-terms.md` C3）。
- [ ] 健康内容讲力量不讲身材，不制造焦虑，没有医疗建议；研究卡三张（防摔、长寿、情绪），出处链到论文原文，观察性研究只写「有关」「相关」；主站的内容里没有训练指导（训练指导在 Veli 里，由持证教练审核）。
- [ ] 中文排版：留白、标点、引号、数字单位、术语大小写都已检查。
- [ ] 英文版按英语读者重写；标题 sentence case；英文页面没有中文正文和未翻译的界面文字。
- [ ] 每种内容的必填字段齐全（PRD 第 5 节）。
- [ ] 图、表、短片都有文字说明，短片有字幕和文字稿。
- [ ] 社交帖子和邮件里的链接带渠道参数。

## 10. 校准

规范和已发布内容都会走样，定期回看：

- **每周**（随每周节奏）：抽查本周发布的内容，每种类型至少一篇，按审阅模式出报告。
- **每月**：对照监测数据（读完率、跳出、订阅转化、搜索词）看哪类内容读不下去，把原因写成规则或检查项；更新 PRD 术语表，把弃用的说法记进「不再用的说法」。
- **一条意见代表一类问题**：用户或审核者指出一个问题时，找出背后的原则，改完所有同类位置，再把原则写回本技能、术语表或检查表；不改的写明理由。产品负责人的输入另在 `docs/requirements/trace.md`「举一反三」一栏写清同类位置和处理，评审和观察者的意见记在 `trace.md` 或 `docs/uiue/decisions.md`（`AGENTS.project.md`「不能越过的线」第 1 条）。
- **校准记录**写进内容运营的过程文档：日期、发现、改了哪些已发布内容、改了哪条规则。
