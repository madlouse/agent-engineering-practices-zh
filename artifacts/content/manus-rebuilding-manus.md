# 用 Manus 重建 Manus：什么变了，什么出了问题，以及我们现在如何工作

作者：张涛，Manus 联合创始人兼首席产品官

九月下旬，在 Manus 2.0 的最后冲刺阶段，我在 Slack 上给一位工程师发了几条功能需求和缺陷报告。后来我去看他进展如何。他的屏幕上开着一排 agent 会话，有的在 Manus 里，有的在 Codex 里。我点进其中一个。提示词就是我在 Slack 上发的消息，一字不差地粘贴进去。

一年前，他会读我的消息，理解我的意思，然后开始写代码。而现在，agent 读取请求，找到相关代码，并提出修改方案。工程师的工作是指挥任务、检查结果并对最终产物负责。大多数时候请求都在运行中，并不需要他等待。如今在我们这里，一名工程师同时推进 10 到 20 个请求已是常态。

我为团队的快速适应感到自豪。但我也感到不安。这个节奏对吗？还有什么是我们没注意到的？

我们在 Manus 构建 agent，所以我们坚持两条原则：用自己的产品做真实工作，并持续寻找 AI 失灵的地方。

我想记录一下当人与 agent 默认并肩工作时，一家公司内部会发生什么。本文涵盖三个团队——工程、产品和市场——并包括那些行不通的地方。这是一份正在进行中的实验报告，而不是对"AI 原生组织"的定义。

我们目前学到的：

- 没有折中之道。把 AI 加到旧的工作方式上有时只会增加噪音。只有当闭环真正形成时，事情才会改变。
- Agent 需要全局视野。更好的上下文比更好的提示词给我们带来的收益更大。
- 信任来自测试和上下文，而不仅仅来自模型质量。
- 自主性需要终点线。只有当成功可被验证时，agent 才能独立运行。在其他所有地方，由人来决定。
- 瓶颈会转移。当工程变得更快时，决定该构建什么反而成了约束。
- 人的角色并未被削弱，反而更聚焦于高影响力的事情。

## 1. 没有折中之道

在 2026 年之前，我们和大多数公司做的事一样：把 AI 加到我们已有的工作方式上。这意味着客服用 AI 摘要来标记问题，工程师使用编程助手，机器人在频道里发布分析。每一块单独看都有用，但各块之间彼此并不相连。在闭环真正形成之前，我们只是在用老办法工作，只不过多了许多 AI 在互相说话。

有一句话我们常常回到：软件工程是随时间累积的编程。写代码容易衡量；让一个复杂产品健康地运行多年则不然。AI 写代码的高占比可能意味着真实的进展，也可能意味着在堆积日后要有人清理的垃圾。

我们真正在意的考验更难。Manus 是一款已上线超过一年的复杂产品。它能否在新的工作方式下持续改进而不崩塌，同时每个人都能做得更多？到目前为止，答案是肯定的。

## 2. 把全局交给 agent

和大多数科技公司一样，我们在交接环节损失的时间最多。前端工程师和后端工程师会各自解读一个需求，就接口达成一致，然后花几天时间修复不匹配的地方。两个人很少会以相同的方式理解同一个需求。

如果 AI 能跨技术栈写代码，是否可以让一个人端到端地负责一个需求？障碍在于上下文。我们的代码分散在不同的仓库中，没有哪个 agent 能一次看到整个系统。

我们对此的回答始于一次内部实验。我们想看看在尽可能少的人工输入和几乎不手写代码的情况下，AI 能把一个产品做到什么程度。我们在这个过程中形成的方法，演变成了如今我们称之为 Manus-mono（或简称 Mono）的内部工具。

Mono 并不合并我们的代码仓库。它是一个统一的入口，加上一份写给 agent 的手册：每个仓库是做什么的、它们如何协作、以及我们是如何工作的。agent 会按需拉取所需内容。我们还维护了一个架构决策记录库，这样每次 agent 会话开始时，获得的不仅是代码，还有过往决策背后的推理。无论谁与 agent 协作，这个 agent 都掌握着此前所有人的上下文。

Mono 是一步步成长起来的，每一步都解决了上一步暴露出的瓶颈：

1. 看清整个系统。我们加入了任何单个仓库都无法涵盖的业务上下文，并使用 Git worktrees 来并行工作。
2. 本地验证。以往推送到测试环境需要 5 到 10 分钟。现在整个 Manus 技术栈可以在一台笔记本上运行，检查只需几秒。
3. 调试生产环境问题。通过受限权限，Mono 可以读取诊断生产环境 bug 所需的日志、配置和错误报告。
4. 端到端执行发布。Mono 现在处理那些以往容易卡住的发布环节。审批决策仍由人来做。
5. 端到端测试。当验证成为瓶颈时，Mono 开始使用测试账户，在浏览器和移动端模拟器中运行真实用户流程。
