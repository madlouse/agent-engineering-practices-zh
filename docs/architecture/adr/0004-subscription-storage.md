# 0004 订阅的存储、发信、退订令牌和频率限制

- 状态：已采纳（产品负责人 2026-11-09 确认；按关口三 b 冷审 P0-1、P1-1 修订；迁移工作流、公开仓库的限制按第二轮冷审 P1-1、P2-6–P2-9、P2-15 补；工作流由主会话维护、迁移约定按第三轮冷审 P1-A、P2-8 补）
- 关联：主站 PRD v2.0 F07 和「订阅的细则」第 1–17 条（第 8 条要求写 ADR 定表结构和同步方式，第 9 条要求定令牌怎么签、多久失效；第 12 条每期的排定和取消、第 17 条邮件内容见 (b)；第 16 条订阅的上线开关见「后果」）；ADR-0003（`/api/site/*`）；PRD 第 3 节路由表 `/unsubscribe`；第三轮冷审 P2-4；关口三 b 冷审 `docs/delivery/reviews/2026-11-09-gate-3b.md` P0-1、P1-2、P1-3、P2-5、P2-9

## 背景

订阅只收邮箱，提交即订阅（细则第 1 条）。要存的有两类：名单（谁在订阅、什么语言、什么状态）和同意证据（每次提交五项）。退订要能一步生效，邮件安全扫描预取链接又不能误退。频率限制要挡住滥用，IP 不能落库（细则第 6 条）。这些都涉及邮箱，按 PRD 第 8 节「安全」打 `risk:high`。

## 决定

**(a) 存储：主站自己的 Supabase 项目，表放在不对外暴露的 schema `site`，只给 `site_api` 角色写策略，不用 service_role。**

- 主站单独一个 Supabase 项目（免费额度），不放进 Veli 的项目：Veli 的项目里有健康数据，主站拿不到它的任何密钥。
- **表放在 schema `site`**，不加进 Supabase Data API 暴露的 schema 列表，公开接口（PostgREST）根本看不到它。
- **迁移里显式收回权限**：`revoke all` 收回 `anon`、`authenticated`、`public` 对 schema `site` 和其中每张表、序列的权限，不靠 Supabase 的默认授权。
- **运行时角色 `site_api`**：能登录，不是表的所有者，不带 `BYPASSRLS`；只授予 `usage on schema site` 和每张表需要的操作。
- **`site` 里的每张表都开行级安全，按表写策略，只给 `site_api` 它需要的操作**：`subscribers` 给 select、insert、update、delete；`consent_records` 给 select、insert（同意证据只增不改，也不给 delete：删订阅者时的级联删除不需要调用者有子表的 delete，见 (e)）；发送记录表给 select、insert（只追加，没有 update、delete，结构见 (b)）。策略写成 `to site_api`；发送记录表另给只读角色 `site_mail_log` 一条 select 的授权和策略（见 (b)），它在别的表上什么也没有。除这两个角色外没有别的策略，一行也读不到。
- **三个连接串，分开用**（第三个 `SITE_DB_MAIL_LOG_URL` 只读发送记录表，见 (b)，订阅打开前才配，放在单独的 GitHub Environment `site-mail-log` 里，不和迁移连接串放在一起）：
  - `SITE_DB_URL`：`site_api` 经 Supabase 连接池（事务模式，用户名是 `site_api.<项目编号>`）的连接串，只放在 Vercel 的生产环境变量里，运行时只读它。
  - `SITE_DB_MIGRATE_URL`：表所有者的连接串，只放在 GitHub 的 Environment `site-db` 里（部署分支只允许 `site`、`feature/v1`，其他分支上的工作流读不到），只由站点迁移脚本在 CI 里读；不进 Vercel，运行时拿不到。
- **迁移只走工作流 `site-db-migrate`**（`.github/workflows/site-db-migrate.yml`），构建命令里不跑迁移。触发只有两种：手动（`workflow_dispatch`）和 `push: site`（只看 `migrations/site/**`），不用 `pull_request`、`pull_request_target`。GitHub 只允许手动触发默认分支上已有的工作流，手动触发时执行的是所选分支上的那份文件。上线前默认分支是 `feature/v1`（`docs/standards/pipeline.md` §5），所以主会话的 `chore/` PR 把文件一次写全放进 `feature/v1`，上线前用 `ref=feature/v1` 手动触发，把迁移跑进生产库；上线合并把文件带进 `site`，上线后默认分支改回 `site`。上线前 `site` 上没有 `migrations/site/`，`push` 不会触发。Environment `site-db` 的部署分支限制配好并核对之前，不手动触发这个工作流（#40）。首次生产迁移后的权限核对是一张单独的票（#67）。迁移日志是公开的：`site:migrate` 不打印连接串或它的片段，驱动错误只输出类别和迁移文件名；迁移只依赖 `pg`，工作流的安装改成 `npm ci --omit=dev --ignore-scripts`（主会话改，#70 安全评审）。
- **工作流文件只由主会话维护**：`.github/workflows/` 是门槛文件，合并脚本拦住改它的票 PR，Agent 会话也没有推送工作流的权限。票只写工作流调用的脚本（`site:migrate`、`scripts/monitor/run.mjs`、`scripts/audit/run.mjs`），并用 `node --test` 断言工作流的配置。
- **迁移约定：向后兼容，先加后删。** `push: site` 触发的迁移和 Vercel 的生产构建同时开始，新代码可能比迁移先上线，旧代码也可能在迁移后还跑一会儿。所以每个迁移都要让新旧两版代码都能跑：加列、加表、加策略可以直接合；删列、改名、改类型、收紧约束拆成两次：先合并兼容的迁移和不再依赖旧结构的代码，等迁移成功、生产部署 READY，再合并删除旧结构的迁移。做不到兼容的改动，先单独合并只含迁移的 PR，等这次运行成功再合并读写新结构的代码。
- **仓库是公开的**：工作流的输入、日志和运行记录谁都看得到。所以删除订阅者、导出同意证据这类要输入邮箱的命令不做成工作流，只在产品负责人本机用 `SITE_DB_URL` 那组 `site_api` 的连接串跑（(e)）。这串连接串只存在 Vercel 的生产环境变量 `SITE_DB_URL` 里，不另存；要用时产品负责人用 `vercel env pull` 取到本机的临时文件，跑完删掉。
- **不碰沙箱契约**：运行时用一个新的服务端模块连 `SITE_DB_URL`，不读预置的 `DATABASE_URL`，不改 `src/lib/db.ts` 和 `src/lib/auth/*`（本仓库 `AGENTS.md`）。加一个检查脚本：`src/` 里读 `SITE_DB_MIGRATE_URL` 的地方为 0；读 `DATABASE_URL` 的地方除沙箱预置的 `src/lib/db.ts`、`src/lib/auth/*` 以外为 0；新模块不引用 `src/lib/db.ts`。
- **连接池的事务模式**不支持命名的预编译语句：驱动关掉它（例如 postgres.js 的 `prepare: false`），否则生产上第一次请求就报错，PGLite 上测不出来。
- **缺连接串时不假装成功**：`VERCEL_ENV=production` 而 `SITE_DB_URL` 缺失或连不上时，订阅接口返回 503，不落到内存库。只有在非生产环境（预览、本地、测试），新模块才用它自己的内存 PGLite，并在启动时执行 `migrations/site/`；PGLite 里没有 `anon`、`authenticated`、`site_api` 时先建同名的不能登录的角色，否则迁移里的 `revoke`、`grant` 会报错；预览上的订阅不写真实名单。
- **预览的多实例**：内存 PGLite 每个函数实例各一份，跨请求的状态（先订阅再退订、重复提交）在 `node --test` 加 PGLite 里测；预览部署上只测界面和单个请求。

| 表 | 字段 |
|---|---|
| `site.subscribers` | `id`（uuid）、`email`（小写后唯一）、`lang`（zh / en）、`status`（active / unsubscribed / stopped_hard_bounce / stopped_complaint / stopped_soft_bounce）、`soft_bounce_streak`、`last_issue_sent`（最近发到第几期，没有发过为空）、`created_at`、`updated_at`、`unsubscribed_at`、`stopped_at` |
| `site.consent_records` | `id`、`subscriber_id`（删订阅者时级联删除）、`email`、`submitted_at`（UTC）、`lang`、`path`（不带查询参数）、`utm_source`、`form_copy_version` |

`last_issue_sent` 给两件事用：每周发送时跳过这一期已经发过的地址（重跑不重复发）；退信回调判断「连续 3 期」软退信时，按期号算。

**(b) 发信：从数据表直接发，不在 Resend 里存第二份名单。**

- 发送前从 `subscribers` 读状态为 active 的地址，按订阅语言用 Resend 的批量发送接口发；这就是细则第 8 条的「发送前同步名单」。Resend 里不建受众（Audience），删除时少一处要删。
- 每封邮件带自己的退订令牌，放进 `List-Unsubscribe`、`List-Unsubscribe-Post` 两个邮件头和正文底部的退订链接。
- Resend 的打开追踪和点击追踪关闭。发信域名 news.velicoach.com（`docs/prd/decisions.md`）。
- 回调 `POST /api/site/resend` 先校验 Resend 的签名（Svix），再按事件编号去重，写回状态。
- 定时：Vercel Cron 触发发送；英文版按 America/New_York 的 08:00 换算，夏令时由处理函数判断。定时接口只接受带 `Authorization: Bearer $CRON_SECRET` 的请求，其余返回 401；密钥用定长比较；`CRON_SECRET` 没配或为空时所有请求都返回 401，不放行。**发送窗口**：处理函数按每种语言的本地时间判断现在是不是这种语言的发送窗口（周日 08:00 起的一小时，中文按北京时间、英文按美国东部时间）；窗口外即使带着正确的 `CRON_SECRET` 也直接返回，不读名单、不写占位行、不发。这样拿到密钥的人或一次手误的调用，不能在周日 08:00 之前把这一期发掉、绕过取消窗口，也不能用掉这一期的占位行（2026-11-11 补，PR #95 安全评审）。**窗口只在一处算**：`scripts/mail-log/send-window.mjs` 里一个函数，给定一种语言和它排定的发送日期，返回三个时刻：窗口开始（当地周日 08:00）、窗口结束（开始后 60 分钟）、宽限结束（窗口结束后 30 分钟）。发送任务和工作流 `site-mail-log` 都调它，不各算各的；时区用 IANA 名（`Asia/Shanghai`、`America/New_York`），不写死偏移，3 月和 11 月的夏令时切换周有用例。**发送任务只在窗口内开跑，开跑以后不再看窗口，最长跑 300 秒**：路由配置的 `maxDuration` 不超过 300（#49 的验收）。所以一次发送最晚在窗口结束后 300 秒内写完结果行或被平台掐断，宽限的 30 分钟比它长。**下文说一种语言「过了宽限」，指过了宽限结束的时刻**；工作流只在这之后才把没有结果行的一期当成已经结束。**定时条目写死在 #49**：中文版一条，英文版按夏令时、冬令时各一条；每条触发时由窗口函数判断当下是不是这种语言的窗口内，不在窗口内的那一次直接返回。
- 预览部署不配 `RESEND_API_KEY`，发信只记一行日志（不带邮箱），不真发。
- **每期一份邮件文件，「当期」按排定的发送日期认**（2026-11-11 补，PRD 细则第 12、17 条）：一期邮件的内容是仓库里的一份文件，由内容车道在周五合并（只用已发布的内容按固定模板拼成）；发送任务只发已经合并的那一份，不在发送时现拼正文。文件里写明期号、邮件票的编号，和每种语言**排定的发送日期**（各自时区的那个周日：中文按北京时间，英文按美国东部时间）。发送任务在某种语言的发送窗口里只发「这种语言排定的发送日期等于当地今天」的那一期：没有这样的文件就不发；日期已经过去的一期永远不会再被当成当期，提前合并的后几期也不会提前发出。`check:mail` 核对这个字段：是日期、是周日、两种语言都有、两种语言是同一个日历日期（同一个周日，各按各的时区）、和别的期不重；新增或改过的邮件文件，排定的发送日期至少比检查当天（UTC）晚两天（周五提的文件排在周日可以，周六提的不行），这样预览进到票里以后离中文版发出也有一天以上。
- **发送前查当期的票**：周五内容车道另开一张票「订阅邮件第 N 期」。发送任务开跑前按下一条读这张票、过核对。**核对不过也留下记录**：「核对不过」指读到了票，但票带 `agent:hold`、已经关闭、身份核对不过，或开得太晚。「开得太晚」两种语言用同一条线：票的 `created_at` 要比**中文版**的窗口开始早至少 24 小时（中文版先发；产品负责人从收到通知到第一封发出至少有一天），不足时这一期两种语言都不发。核对不过时这种语言不发，并且照样插入占位行，再插入一条结果行（带 `agent:hold` 是 `stopped_hold`，其余是 `stopped_ticket`）。这样「取消的这一期不补发」是库里的事实：之后有人重开这张票或去掉 `agent:hold`，占位行已经在，不会再发。**读票失败不留记录，也不再试**：只有 HTTP 200、JSON 解析成功、核对要用的字段（`user.id`、`author_association`、`title`、`state`、`labels`、`created_at`，以及没有 `pull_request`）都齐全，才算读到了票、进入核对；其余一律是读票失败：404、410、301（票被转移）、403、429、5xx、超时、解析不出来、缺字段。开跑前读票失败时，这一期这种语言不发、不写任何行，进当天的日报。拿不准的都归到读票失败，因为它不在库里留下「已停」的记录，票里会如实记成「未发」。发送任务自己不写 GitHub；在票里记录并关票由一个单独的工作流做（见下面「由工作流在邮件票里记录」）。
- **每期每种语言只发一次，发送记录表只追加**：(a) 的 schema `site` 里加一张发送记录表，随发信的票建迁移。列有期号、语言、`kind`、`outcome`、时间、封数、失败数，没有邮箱；`kind` 只有两种取值：`claim` 是占位，`result` 是结果；唯一键是（期号，语言，`kind`）。结果行的 `outcome` 写这一期是怎么结束的，取值固定四种：`complete`（发完）、`stopped_hold`（票带 `agent:hold`）、`stopped_ticket`（票已关闭或核对不过）、`stopped_error`（读票失败或发信出错停下）；占位行的 `outcome` 为空。结果行都带已发的封数和失败数，停在哪一步不从封数里猜。约束都写在迁移里：`kind` 和 `outcome` 各一条限定取值的 check；一条跨列的 check，`(kind = 'claim' and outcome is null) or (kind = 'result' and outcome is not null)`（只限定取值不够：`outcome in (…)` 遇到空值是通过的，结果行会没有 `outcome`、占位行会带着 `outcome`）；语言只能是 `zh`、`en`；封数和失败数不小于 0；期号在 1 到 9999 之间。发送任务发信前先插入（期号，语言，`claim`）一行，这一行就是锁：插入冲突（已经有了）就不发。发完或被拦停时插入（期号，语言，`result`）一行，带 `outcome`、时间、封数和失败数：事后看记录分得出是发完了还是只发了前几批。两种行都只插入、不改：`site_api` 对这张表只有 select、insert，没有 update、delete；`site_mail_log` 只有 select。「已发」以占位行为准，不以邮件票的状态为准；只有占位行、没有结果行，说明这一次发送中途断了、没来得及记结果，不补发。票被重开、任务被重复触发、内容推进器停摆时都不会重发。（2026-11-11 按 PR #95 安全评审 B1 写死：唯一键只有期号加语言时，结果行插不进去，实现时只能给 `site_api` 加 update 或放宽唯一键，两条都破坏不变量。）
- **按票号读票，不按标题搜**：当期邮件文件里写死邮件票的编号。发送任务按编号读票，过两部分核对，有一项不符就不发。**身份核对**（发送任务和下面的工作流共用一个函数，放在 `scripts/mail-log/ticket-identity.mjs`）：是 issue 不是 PR；作者的数字 `user.id` 等于仓库所有者的编号，且 `author_association` 是 `OWNER`（和「产品负责人的回复」的判法一致，不按登录名比：登录名可以改，旧名会被别人注册）；标题按锚定的正则解析出「订阅邮件第 N 期」的期号，和邮件文件的期号一致（写死的票号只能证明「这是仓库所有者开的一张 issue」）。**状态核对**（只有发送这一侧做）：票开着、没有 `agent:hold`。发送任务每批发出前重读一次邮件票（第一批也是）：票带 `agent:hold` 就停下（`stopped_hold`），票被关就停下（`stopped_ticket`），这时读票失败或发信出错也停下（`stopped_error`）。已发的封数和失败数记进结果行，这样取消也能拦住正在发的一期。读票用一个只读的 GitHub 令牌（进密钥清单），发送任务不写 GitHub。
- **由工作流在邮件票里记录**（2026-11-11 定，关口三 b 冷审 P1-10 的做法 (b)）：一个 GitHub Actions 工作流 `site-mail-log`（主会话维护，跑在单独的 GitHub Environment `site-mail-log` 里，里面只有 `SITE_DB_MAIL_LOG_URL`；不用 `site-db`，那里有表所有者的连接串，一次写错的 `secrets` 引用就会让只读角色这层隔离白做）用只读角色 `site_mail_log` 的连接串 `SITE_DB_MAIL_LOG_URL` 读发送记录表的七列（期号、语言、`kind`、`outcome`、时间、封数、失败数；没有邮箱），用工作流自带的 `GITHUB_TOKEN`（`issues: write`）按邮件文件里的票号在邮件票里写一条评论（首行 `<!-- vc-bot role=邮件记录 -->`）并关票。**触发和权限写死**：触发只有 `schedule` 和不带输入的 `workflow_dispatch`，没有 `pull_request`、`pull_request_target`、`issues`、`issue_comment`、`workflow_run`；job 的 `permissions` 只有 `contents: read` 和 `issues: write`；票号只从检出的邮件文件读，经环境变量传给脚本，不在 `run:` 里用 `${{ }}` 拼。它的令牌能改仓库里任何 issue 和标签（包括 #13 的总开关），所以脚本只发两种请求：给这一张票写评论、把这一张票关掉。**处理哪些、写什么、什么时候关票（只在这里定义一次，PRD、`pipeline.md`、`content-runner.md` 和票都指到这里，不另抄一遍）**：脚本每次运行看所有已合并的邮件文件，处理其中「两种语言都过了宽限、文件里的邮件票上还没有记录评论」的每一份；别的不碰。「记录评论」只认作者是 GitHub Actions 机器人（`user.login` 是 `github-actions[bot]`、`user.type` 是 `Bot`）、首行带标记的评论，别人仿写的不算。这条规则可以重复跑：上一期已经有记录评论，不再写；提前合并的下一期还没过宽限，不处理；漏跑的一期没有记录评论，下一次运行自然补上。处理一份文件就是过身份核对、写一条记录评论、票开着就关（已经关着就不动）。产品负责人用关票取消的一期、发到中途被关票拦停的一期，票里因此也有记录。评论里每种语言一行，写「结果，已发 N 封、失败 M 封」，结果只按发送记录里有什么行、`outcome` 是什么来定，对照表只有六行：

  | 发送记录里这种语言有什么 | 记成 |
  |---|---|
  | 结果行 `complete` | 发完 |
  | 结果行 `stopped_hold` | 因 `agent:hold` 停下 |
  | 结果行 `stopped_ticket` | 因邮件票已关闭或核对不过停下 |
  | 结果行 `stopped_error` | 出错停下（封数以 Resend 的发送日志为准） |
  | 有占位行、没有结果行 | 发送中途断了（封数以 Resend 的发送日志为准），不写封数 |
  | 两种行都没有 | 未发，不写封数 |

  **已有记录评论的一期只剩一件事**：票还开着就关掉（上一次评论写成了、关票没成的，这一次补上）；不写第二条评论。**定时写死**：工作流的 cron 用 UTC，三次：`45 14 * * 0`、`45 16 * * 0`、`45 2 * * 1`，都在英文版宽限结束（UTC 周日 13:30 或 14:30，随夏令时）之后；cron 只决定什么时候跑，处理哪些由脚本用共用的窗口函数判断。工作流加 `concurrency`，同一时间只跑一个。**没有邮件文件的一期不归工作流**：周五邮件文件没能合并的一期，票由内容推进器关（`docs/delivery/loops/content-runner.md` 周五第 2 件），邮件文件合并以后推进器不再关这张票。**写票之前的核对**：邮件文件里的票号是内容车道能改的数据，工作流又拿着能写票的令牌，所以写评论、关票之前过上一条的身份核对（同一个函数）；有一项不符就不写不关，只在工作流日志里报错。**一份文件出错不挡别的文件**：脚本逐份处理，一份过不了身份核对或读不到票，记下来、继续处理其余的，全部处理完再以非 0 退出。那份文件确认有问题时，由主会话提 PR 删掉它，在 #13 记一笔（删除文件不过「日期至少晚两天」的检查）；邮件票的标题不要改，改了就过不了身份核对。带 `agent:hold` 的票照样记录并关掉。工作流照迁移工作流的加固写法（#73）：action 固定到完整的提交 SHA、checkout 不留凭据、安装不跑安装脚本；它调用的 `scripts/mail-log/`（含共用的身份核对函数）和工作流文件 `.github/workflows/site-mail-log.yml` 都进合并脚本的高风险文件清单，改它们的 PR 都要安全评审（#91）；放入 `SITE_DB_MAIL_LOG_URL` 之前，工作流文件先过一次独立的安全评审（#89）。`site_mail_log` 不带 `BYPASSRLS`，只有发送记录表的 select 授权和策略，读不到 `subscribers` 和 `consent_records`。角色由迁移建成不能登录的（`nologin`），授权和策略也写在迁移里，这样上线前的首次生产迁移不依赖任何人工步骤；订阅打开前，产品负责人只做一件事：把它改成能登录、设密码，把连接串放进 `site-mail-log` 环境（#96，排在上线前的权限核对 #67 之后：#67 核对的是上线时它还不能登录）。不为这件事加公开接口，内容推进器不读发送记录、也拿不到任何数据库连接串。没有选的两种做法：`/api/site/` 下加只读接口（多一个公开接口和一个密钥）；发送任务把结果写进运行时日志由推进器读（依赖日志保留期）。
- **一期邮件票的时间线**（上面各条是定义，这张表是它们按时间排起来的样子；两处不一致时以定义为准并改这张表）。T 是一种语言的窗口开始（当地周日 08:00），T中 是中文版的窗口开始（UTC 周日 00:00）。

  | 时刻 | 谁 | 看到什么 | 写什么 |
  |---|---|---|---|
  | 周五，最晚 T中−24 小时（北京时间周六 08:00） | 内容推进器 | 订阅的上线开关开着 | 开邮件票「订阅邮件第 N 期」、@ 产品负责人、锁定对话；赶不上就不开，这一期不排 |
  | 开票之后 | 内容推进器、评审 | 票的编号 | 提邮件文件的 PR 并合并（`check:mail`：排定的发送日期至少比检查当天晚两天），把预览补进票里；周五结束前文件没合并，推进器关票 |
  | 开票到 T | 产品负责人 | 票里的预览和最晚取消时间 | 要取消就打 `agent:hold` 或关票 |
  | 定时触发，不在窗口内；或开关关着、没有当期文件、当期文件去掉已撤下的条目后没有条目、已有占位行 | 发送任务 | — | 不写，返回（票里按对照表最后一行记「未发」） |
  | 窗口内，开跑前读票失败 | 发送任务 | 不是「200、解析成功、字段齐全」 | 不写行，进日报，这一期这种语言不发 |
  | 窗口内，核对不过 | 发送任务 | `agent:hold`、已关、身份不符、票开得太晚 | 占位行加结果行（`stopped_hold` 或 `stopped_ticket`） |
  | 窗口内，核对通过 | 发送任务 | 票开着、没有 `agent:hold` | 占位行，然后分批发；每批发出前重读票，要停就写结果行（`stopped_hold`、`stopped_ticket`、`stopped_error`）；发完写 `complete` |
  | 开跑后 300 秒 | 平台 | 函数到了 `maxDuration` | 被掐断的一次只有占位行 |
  | UTC 周日 14:45、16:45，周一 02:45 | 工作流 `site-mail-log` | 所有已合并的邮件文件、发送记录、票 | 两种语言都过了宽限、票上还没有记录评论的每一份：过身份核对，写一条记录评论，票开着就关。已有记录评论、票还开着的：只关票 |
  | 周二 | 内容推进器 | 周日的邮件票还开着 | 写进当天的日报 |
  | 任何时候 | 产品负责人 | — | 紧急关：之后的触发不发、不写行，在跑的一次管不到（`docs/delivery/launch-runbook.md`「再关上」）。一期出了错要重来：不删发送记录的行，用新的期号、新票、新文件排到下一个周日 |

  走过的三种情况：占位行写完、第一批就出错，结果行是 `stopped_error`，票里记「出错停下」，函数没来得及写结果行就记「发送中途断了」，两种都不写成未发；上一期、当期、提前合并的下一期三份文件并存时，发送任务只认排定日期等于当地今天的那一份，工作流只处理过了宽限、还没有记录评论的那一份；票在 UTC 周六中午才开出来，两种语言都记 `stopped_ticket`，这一期不发。

- **发送时再核对一遍条目，放在读票和占位之前**：邮件里链到的内容已撤下，去掉那一条；去掉以后没有条目，这种语言不发、不读票、不写任何行，直接返回，票里按对照表最后一行记「未发」。

**(c) 退订令牌：HMAC 签名，365 天失效，密钥可轮换。**

- 令牌 = 密钥编号、订阅者 `id`、签发日期，加上用 `SUBSCRIBE_TOKEN_SECRET_<编号>` 算的 HMAC-SHA256，base64url 编码。令牌里没有邮箱。
- 签发 365 天后失效（自定：美国 CAN-SPAM 要求退订链接至少 30 天内可用；邮件会被翻出来再看，所以取一年）。
- 换密钥时加一个新编号，旧编号继续验证 365 天后删掉。
- 篡改、过期、密钥编号已删、订阅者已删除：`/unsubscribe` 页显示「这个退订链接已失效」，给联系邮箱；不透露这个地址在不在名单里。
- `GET /unsubscribe?token=…` 只显示页面，不改数据；「确认退订」按钮和邮件头的一键退订都走 `POST /api/site/unsubscribe`。

**(d) 频率限制：IP 只在内存里，邮箱按数据表算。**

- 同一 IP 每小时 5 次：在接口进程的内存里计数，1 小时过期，不落库，不写日志。多个实例各算各的，实际放行的次数可能多于 5 次。产品负责人 2026-11-09 同意按实例计数，PRD 细则第 6 条已写明；Vercel 套餐确认以后，可以在防火墙加同样的规则作为第二道。
- 同一邮箱每小时 3 次：每次提交都存一条同意证据（细则第 2 条），所以数 `consent_records` 里这个邮箱最近 1 小时的条数；被限流挡掉的提交不存。
- 超过任一限制返回 429。不用验证码（`quality-terms` X5）。

**(e) 删除：一条命令，30 天内做完。**

按邮箱删 `site.subscribers`（级联删同意证据），再调用 Resend 的接口删能删的。命令在产品负责人本机用 `site_api` 的连接串跑（`site_api` 只有 `subscribers` 的 delete 授权和策略；`consent_records` 靠外键的级联删除跟着删，级联由数据库以表所有者的身份执行，不需要调用者有子表的 delete，也不受子表行级安全的限制。2026-11-11 在 PGLite（PostgreSQL 18.3）上核对过：`site_api` 直接删 `consent_records` 被拒，删 `subscribers` 的一行以后它的同意证据一并消失。所以 `consent_records` 不给 delete：泄露的运行时连接串抹不掉单条同意证据；生产上由 #67 再核对一次），不用所有者连接串，也不做成 GitHub Actions 的工作流：仓库是公开的，运行的输入和日志会泄露邮箱。Resend 不存名单（(b)），留下的只有发送日志：删除那张票查明所用 Resend 套餐的日志保留期并写进运行手册和隐私评审清单；保留期超过 30 天，就和 PRD 第 8 节「隐私」「删除订阅记录后 Resend 里查不到这个邮箱」不一致，算需求偏差，交产品负责人和律师。运行手册另写一条查询命令：按邮箱拿出这个订阅者全部的同意证据。

## 考虑过的其他做法

| 做法 | 为什么不选 |
|---|---|
| 放进 Veli 的 Supabase 项目 | 主站要拿那个项目的连接串，健康数据和订阅名单在同一个权限边界里 |
| 用 Resend 的受众和广播管理退订 | 退订在 Resend 那边，`/unsubscribe` 页和同意证据要两边对账；Resend 里多一份名单，删除要删两处 |
| 用 Redis 之类的外部存储做 IP 限流 | 多一家服务商，隐私评审的第三方清单多一行；v1 先用内存计数加邮箱限流和一键退订，上线两周后按数据复核 |
| 表放在 `public`，靠 `revoke` 加策略挡公开接口 | 少一道：只要有人改了 Supabase 的默认授权或加错一条策略，公开接口就能读到邮箱；单独的 schema 不暴露，公开接口从根上看不到 |
| 运行时沿用 `src/lib/db.ts` 和 `DATABASE_URL` | 那是沙箱预置的模块，登录模块也读 `DATABASE_URL`；所有者连接串进了运行时，行级安全形同虚设；缺变量时静默落到内存库，订阅会丢 |
| 令牌不失效 | 泄露的旧链接永远可用；失效以后还有联系邮箱这条路 |

## 后果

- 紧急关（2026-11-11 补，PR #84 安全评审的建议）：读开关的函数另读环境变量 `SUBSCRIBE_FORCE_OFF`，任何非空且不是 `0` 的值都算关，不管站点配置是什么；只能关、不能开，往关的方向失败（紧急时填成 `true`、`yes` 或多打一个空格也是关）。产品负责人在 Vercel 后台设上并点重新部署就生效，不用等 PR、评审和合并。一个开关管两件事，因为接口、页面和发送任务调的是同一个函数：订阅表单不显示、订阅接口返回 404，之后开跑的发送任务也不发；退订和 Resend 回调照常可用。**它管不到已经在跑的那一次发送**：环境变量要重新部署才生效，正在跑的调用读的还是旧值。已经在发时有两个办法：给当期邮件票打 `agent:hold` 或关掉它，发送任务每批发出前重读邮件票，会在批与批之间停下；要立刻停，直接在 Resend 后台删掉 API key，不必先试别的。Resend 没有「停用」，删了撤不回，恢复要新建一个 key、更新 Vercel 的 `RESEND_API_KEY` 并重新部署；发送任务是先写占位行再发，删 key 以后这一期按已发算、失败数照实记进结果行，这一期不补发。
