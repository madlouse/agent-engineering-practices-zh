# 0005 外部监控和告警：GitHub Actions 定时探测，不加新服务商

- 状态：待产品负责人确认（2026-11-09，关口三 b 冷审 P1-4 后写）
- 关联：PRD v1.2 第 8 节「可靠性」（外部监控、连续 2 次失败发邮件、按月算可用率，「监控工具在关口三 b 写 ADR 选定」）、「可观测性」（「错误告警的工具、阈值和渠道在关口三 b 写 ADR 定」）、F29；ADR-0003 (a) `GET /api/site/health`；ADR-0004；`docs/standards/observer.md`

## 背景

PRD 要两件事：主站挂了有人知道（外部探测、连续两次失败才告警、按月算可用率），线上报错有人知道。PRD 也要求架构选型极简：先用免费额度，第三方越少，隐私评审的第三方清单越短。

## 决定

**(a) 可用性：GitHub Actions 定时任务做外部探测。**

- 主站仓库加一个定时工作流，每 10 分钟请求一次：首页 `/`、`/mind`、一篇文章页和 `GET /api/site/health`。任何一个返回非 2xx 或 10 秒内没有响应，记一次失败。
- **告警**：连续两次失败，在本仓库开一个 issue（标题写哪个地址、从什么时候开始失败），正文 @ 产品负责人的 GitHub 账号；GitHub 按产品负责人的通知设置发邮件。已经有一个没关的告警 issue 时只在里面加评论，不重复开。恢复后自动在 issue 里写恢复时间并关掉。
- **可用率**：每次探测把结果（时间、地址、状态码、耗时）写进这次运行的摘要和结论（全部通过为成功）；每月 1 日由同一个工作流用 GitHub 的运行记录接口（保留 90 天）算出上个月的可用率，写进一个固定的 issue 评论，日报引用它。不往仓库里提交探测数据。
- **为什么是 10 分钟**：GitHub 的定时任务在高峰时会延迟、最短间隔 5 分钟也不保证准点；10 分钟加「连续两次」，等于主站连续不可用约 20 分钟才告警。PRD 写的是每 5 分钟，这个改动要在线 PRD 跟着改（`docs/delivery/gate-3b-split.md` §9）。
- 探测请求不带 Cookie、不带任何个人数据；工作流只用 GitHub 自带的 `GITHUB_TOKEN`（开 issue 的权限），不需要新的密钥。

**(b) 线上错误：Pro 之前进日报，Pro 之后用 Vercel 的告警。**

- Vercel 套餐升级为 Pro 之前：每日的观察者循环用 Vercel 的运行时错误接口拉过去 24 小时主站生产部署的错误，按路径和错误类型汇总进日报（`docs/delivery/loops/observer.md`）；同一类错误一天超过 10 次（自定），写进日报的「等你决定」。
- 升级为 Pro 之后：打开 Vercel 的错误告警，阈值同上，发到产品负责人的邮箱；日报的汇总保留。
- 日志和错误里不出现邮箱、令牌和健康数据（PRD 第 8 节「可观测性」），由订阅票和 #61 的隐私评审检查。

**(c) 健康检查接口。**

`GET /api/site/health` 检查数据库（`SITE_DB_URL` 上执行一次 `select 1`）和发信配置（`RESEND_API_KEY` 存在），都通过返回 200，否则返回 503；正文只有每项的「ok / fail」，不带密钥、连接串和邮箱。

## 考虑过的其他做法

| 做法 | 为什么不选 |
|---|---|
| UptimeRobot、Better Stack 一类的探测服务 | 多一家服务商和一个账号，隐私评审多一行；免费额度能不能用于商业站要逐家核对 |
| Vercel Cron 自己探测自己 | 不是外部监控：Vercel 整体出问题时探测也一起停 |
| 只靠日报看错误 | 主站整站挂了要等到第二天早上才知道 |

## 后果

- 不新增服务商；第三方清单里的「监控工具」就是 GitHub（只收到探测结果，没有个人数据）。
- GitHub 定时任务可能延迟或在仓库 60 天没有活动时被停用；观察者每周看一次探测记录有没有断档。
- 告警渠道依赖产品负责人在 GitHub 上打开了邮件通知；告警 issue 的测试由关口四的清单核对（产品负责人回复收到）。
- 实现在监控票里（`docs/delivery/gate-3b-split.md`）；Pro 生效后的 Vercel 错误告警在升级 Pro 那张票里配。
