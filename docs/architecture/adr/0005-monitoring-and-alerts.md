# 0005 外部监控和告警：GitHub Actions 定时探测，不加新服务商

- 状态：已采纳（2026-11-09；主会话按「不加新服务商」定，产品负责人同日确认升级 Vercel Pro；(b) 按关口三 b 第二轮冷审 P1-4 改：不加 Observability Plus，错误照旧进日报）
- 关联：PRD v1.2 第 8 节「可靠性」（外部监控、连续 2 次失败发邮件、按月算可用率，「监控工具在关口三 b 写 ADR 选定」）、「可观测性」（「错误告警的工具、阈值和渠道在关口三 b 写 ADR 定」）、F29；ADR-0003 (a) `GET /api/site/health`；ADR-0004；`docs/standards/observer.md`

## 背景

PRD 要两件事：主站挂了有人知道（外部探测、连续两次失败才告警、按月算可用率），线上报错有人知道。PRD 也要求架构选型极简：先用免费额度，第三方越少，隐私评审的第三方清单越短。

## 决定

**(a) 可用性：GitHub Actions 定时任务做外部探测。**

- 主站仓库的工作流 `site-monitor`（`.github/workflows/site-monitor.yml`）每 10 分钟请求一次：首页 `/`、`/mind`、一篇文章页和 `GET /api/site/health`。任何一个返回非 2xx 或 10 秒内没有响应，记一次失败。
- **上线前就能跑**：GitHub 的定时任务只跑默认分支 `site` 上的工作流，手动触发也只认 `site` 上已有的文件。所以这个文件先由主会话的 `chore/` PR 放进 `site`（定时也写上，脚本不存在或没有探测目标时什么也不做）；上线前用 `ref=feature/v1` 手动触发演练告警，上线合并后定时生效。探测目标是仓库变量 `MONITOR_TARGET`：合并后到切换之前是主站生产部署的固定地址，切换后是 `https://velicoach.com`（`docs/delivery/launch-runbook.md`）。
- **告警**：连续两次失败，在本仓库开一个 issue（标题写哪个地址、从什么时候开始失败），正文 @ 产品负责人的 GitHub 账号；GitHub 按产品负责人的通知设置发邮件。已经有一个没关的告警 issue 时只在里面加评论，不重复开。恢复后自动在 issue 里写恢复时间并关掉。
- **可用率**：每次探测把结果（时间、地址、状态码、耗时）写进这次运行的摘要和结论（全部通过为成功）；每月 1 日由同一个工作流用 GitHub 的运行记录接口（保留 90 天）算出上个月的可用率，写进一个固定的 issue「主站可用率」的评论（监控票第一次运行时建，号码存进仓库变量 `MONITOR_UPTIME_ISSUE`；不用状态 issue #13），日报引用它。不往仓库里提交探测数据。
- **机器人标记**：工作流写的每一条 issue 正文和评论，首行都是 `<!-- vc-bot role=监控 -->`；不带它的评论会被推进器当成产品负责人的回复。
- **为什么是 10 分钟**：GitHub 的定时任务在高峰时会延迟、最短间隔 5 分钟也不保证准点；10 分钟加「连续两次」，等于主站连续不可用约 20 分钟才告警。PRD 原来写每 5 分钟，在线第 269 版已改成每 10 分钟。
- 探测请求不带 Cookie、不带任何个人数据；工作流只用 GitHub 自带的 `GITHUB_TOKEN`（`issues: write` 开 issue，`actions: read` 读运行记录算可用率，`contents: read`），不需要新的密钥。

**(b) 线上错误：进每日日报；Pro 之后加开 Vercel 内置的异常检测告警作补充。**

- 每日的观察者循环用 Vercel 的运行时错误接口拉过去 24 小时主站生产部署的错误，按路径和错误类型汇总进日报（`docs/delivery/loops/observer.md`）；升级 Pro 前后都一样，这是线上错误的主渠道。同一类错误一天超过 10 次（自定），写进日报的「等你决定」。
- 升级为 Pro 之后：打开 Vercel 内置的错误异常告警，发到产品负责人的邮箱，作为补充。它按 Vercel 自己的基线做异常检测，不能设次数阈值，所以不写「一天多少次」。
- 不加 Observability Plus：按次数设阈值的告警和自定监控要另付这一项，产品负责人确认的只有 Pro（PRD 第 8 节「成本」）。整站挂了由 (a) 的外部探测在约 20 分钟内告警，已经覆盖。
- 日志和错误里不出现邮箱、令牌和健康数据（PRD 第 8 节「可观测性」），由订阅票和 #61 的隐私评审检查。

**(c) 健康检查接口。**

`GET /api/site/health` 检查数据库（`SITE_DB_URL` 上执行一次 `select 1`）和发信配置（`RESEND_API_KEY` 存在），都通过返回 200，否则返回 503；正文只有每项的「ok / fail」，不带密钥、连接串和邮箱。结果在服务端缓存 30 秒（自定），挡住拿它刷数据库连接池；探测每 10 分钟一次，不受缓存影响。

## 考虑过的其他做法

| 做法 | 为什么不选 |
|---|---|
| UptimeRobot、Better Stack 一类的探测服务 | 多一家服务商和一个账号，隐私评审多一行；免费额度能不能用于商业站要逐家核对 |
| Vercel Cron 自己探测自己 | 不是外部监控：Vercel 整体出问题时探测也一起停 |
| 只靠日报看错误 | 主站整站挂了要等到第二天早上才知道（所以有 (a)） |
| 加 Observability Plus，按「同一类一天超过 10 次」设阈值告警 | 多一个产品负责人没确认的收费项；整站挂了 (a) 已经覆盖，零星错误进日报一天内能看到 |

## 后果

- 不新增服务商；第三方清单里的「监控工具」就是 GitHub（只收到探测结果，没有个人数据）。
- GitHub 定时任务可能延迟或在仓库 60 天没有活动时被停用；观察者每周看一次探测记录有没有断档。
- 告警渠道依赖产品负责人在 GitHub 上打开了邮件通知；告警 issue 的测试由关口四的清单核对（产品负责人回复收到）。
- 实现在监控票里（`docs/delivery/gate-3b-split.md`）；Pro 生效后打开 Vercel 内置异常告警，在升级 Pro 那张票里做。
