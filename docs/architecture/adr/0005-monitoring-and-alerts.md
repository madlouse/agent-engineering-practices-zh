# 0005 外部监控和告警：GitHub Actions 定时探测，不加新服务商

- 状态：已采纳（2026-11-09；主会话按「不加新服务商」定，产品负责人同日确认升级 Vercel Pro；(b) 按关口三 b 第二轮冷审 P1-4 改：不加 Observability Plus，错误照旧进日报；第三轮冷审 P1-B 删掉了「Pro 之后开 Vercel 内置异常告警」）
- 关联：PRD v1.2 第 8 节「可靠性」（外部监控、连续 2 次失败发邮件、按月算可用率，「监控工具在关口三 b 写 ADR 选定」）、「可观测性」（「错误告警的工具、阈值和渠道在关口三 b 写 ADR 定」）、F29；ADR-0003 (a) `GET /api/site/health`；ADR-0004；`docs/standards/observer.md`

## 背景

PRD 要两件事：主站挂了有人知道（外部探测、连续两次失败才告警、按月算可用率），线上报错有人知道。PRD 也要求架构选型极简：先用免费额度，第三方越少，隐私评审的第三方清单越短。

## 决定

**(a) 可用性：GitHub Actions 定时任务做外部探测。**

- 主站仓库的工作流 `site-monitor`（`.github/workflows/site-monitor.yml`）每 10 分钟请求一次：首页 `/`、`/mind`、一篇文章页和 `GET /api/site/health`。任何一个返回非 2xx 或 10 秒内没有响应，记一次失败。
- **上线前就能跑**：GitHub 的定时任务只跑默认分支上的工作流，手动触发也只认默认分支上已有的文件。上线前默认分支是 `feature/v1`（`docs/standards/pipeline.md` §5），所以这个文件由主会话的 `chore/` PR 一次写全放进 `feature/v1`，在上面就能手动触发和定时运行（脚本不存在或没有探测目标时什么也不做）；上线合并把文件带进 `site`，上线后默认分支改回 `site`。工作流文件只由主会话维护，监控票只写 `scripts/monitor/run.mjs`；演练告警用手动触发的 `target` 输入，地址也要在允许清单里：用一个没有部署的 `*.vercel.app` 子域名（`https://velicoach-drill-404.vercel.app`，Vercel 对它返回 404），演练前先请求一次，确认是 404 再触发。探测目标是仓库变量 `MONITOR_TARGET`：上线合并、生产部署有了 `/api/site/health` 之后才设（之前设会误报），到切换之前是主站项目的生产域名（`*.vercel.app`），切换后是 `https://velicoach.com`（`docs/delivery/launch-runbook.md`）。
- **工作流和脚本的接口**：工作流给脚本的环境变量是 `MONITOR_TARGET`（探测的主机地址）、`MONITOR_EVENT_SCHEDULE`（定时触发时是 cron 串，等于 `17 1 1 * *` 时算可用率，手动触发时为空）、`MONITOR_BOT_HEADER`（机器人标记）和 `GH_TOKEN`；脚本是 `node scripts/monitor/run.mjs`，不带参数。
- **告警**：连续两次失败，在本仓库开一个 issue（标题以固定前缀「主站告警：」开头，写哪个地址、从什么时候开始失败），正文 @ 产品负责人的 GitHub 账号；GitHub 按产品负责人的通知设置发邮件。已经有一个没关的告警 issue（按标题前缀认，不按标签：可用率 issue 也带 `monitor`）时只在里面加评论，不重复开；只有「主站可用率」开着时照样新开告警。恢复后自动在 issue 里写恢复时间并关掉。
- **可用率**：每次探测把结果（时间、地址、状态码、耗时）写进这次运行的摘要和结论（全部通过为成功）；每月 1 日由同一个工作流用 GitHub 的运行记录接口（保留 90 天）算出上个月的可用率，写进一个固定的 issue「主站可用率」的评论；不用状态 issue #13，日报引用它。脚本按固定标题「主站可用率」加标签 `monitor` 找这个 issue，找不到就新建；不用仓库变量存号码（`GITHUB_TOKEN` 读写不了仓库变量），工作流也不用为它改。不往仓库里提交探测数据。
- **机器人标记**：工作流写的每一条 issue 正文和评论，首行都是 `<!-- vc-bot role=监控 -->`；漏了它，这条评论可能被推进器当成产品负责人的回复（判法见 `pipeline.md` §6）。
- **为什么是 10 分钟**：GitHub 的定时任务在高峰时会延迟、最短间隔 5 分钟也不保证准点；10 分钟加「连续两次」，等于主站连续不可用约 20 分钟才告警。PRD 原来写每 5 分钟，在线第 269 版已改成每 10 分钟。
- **仓库是公开的**：告警 issue、评论、运行摘要和日志里只写时间、地址、状态码、耗时，不写响应体和响应头。`MONITOR_TARGET` 只接受 `https://` 且主机在允许清单里（`velicoach.com`、`*.vercel.app`），不跟随跳转到别的主机；写进 issue 前转义 Markdown 和 `@`（#70 安全评审）。
- 探测请求不带 Cookie、不带任何个人数据；工作流只用 GitHub 自带的 `GITHUB_TOKEN`（`issues: write` 开 issue，`actions: read` 读运行记录算可用率，`contents: read`），不需要新的密钥。

**(b) 线上错误：进每日日报，不开 Vercel 的告警。**

- 每日的观察者循环用 Vercel 的运行时错误接口拉过去 24 小时主站生产部署的错误，按路径和错误类型汇总进日报（`docs/delivery/loops/observer.md`）；升级 Pro 前后都一样，这是线上错误唯一的告警渠道。同一类错误一天超过 10 次（自定），写进日报的「等你决定」。
- Vercel 的告警（包括内置的错误异常告警和按次数设阈值的自定监控）要另付 Observability Plus，不开：产品负责人确认的只有 Pro（PRD 第 8 节「成本」）。整站挂了由 (a) 的外部探测在约 20 分钟内告警，已经覆盖。
- 日志和错误里不出现邮箱、令牌和健康数据（PRD 第 8 节「可观测性」），由订阅票和 #61 的隐私评审检查。

**(c) 健康检查接口。**

`GET /api/site/health` 检查数据库（`SITE_DB_URL` 上执行一次 `select 1`）和发信配置（`RESEND_API_KEY` 存在），都通过返回 200，否则返回 503；正文只有每项的「ok / fail」，不带密钥、连接串和邮箱。结果在服务端缓存 30 秒（自定），挡住拿它刷数据库连接池；探测每 10 分钟一次，不受缓存影响。

## 考虑过的其他做法

| 做法 | 为什么不选 |
|---|---|
| UptimeRobot、Better Stack 一类的探测服务 | 多一家服务商和一个账号，隐私评审多一行；免费额度能不能用于商业站要逐家核对 |
| Vercel Cron 自己探测自己 | 不是外部监控：Vercel 整体出问题时探测也一起停 |
| 只靠日报看错误 | 主站整站挂了要等到第二天早上才知道（所以有 (a)） |
| 加 Observability Plus，打开 Vercel 的告警 | 多一个产品负责人没确认的收费项；整站挂了 (a) 已经覆盖，零星错误进日报一天内能看到 |

## 后果

- 不新增服务商；第三方清单里的「监控工具」就是 GitHub（只收到探测结果，没有个人数据）。
- GitHub 定时任务可能延迟或在仓库 60 天没有活动时被停用；观察者每周看一次探测记录有没有断档。
- 告警渠道依赖产品负责人在 GitHub 上打开了邮件通知；告警 issue 的测试由关口四的清单核对（产品负责人回复收到）。
- 实现在监控票 #59 里；工作流文件由主会话维护。
