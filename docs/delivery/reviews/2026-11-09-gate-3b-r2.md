## P1（开工前必须改）

### P1-1 GitHub Actions 的工作流上线前跑不起来：#40 和 #45 之间有一个靠验收形成的环

位置：#40 验收第 5 条「#45 的迁移第一次在生产跑完后，Supabase 安全顾问 0 个问题」；#45 备注第 1 条（迁移工作流「手动触发和生产分支合并后触发」）；#59 验收第 5 条（手动触发、连跑两次）；ADR-0004 (a) 迁移那一条、ADR-0005 (a)；`pipeline.md` §5「上线前两条车道的 PR 都合并回 `feature/v1`」；默认分支 `site`。

1. GitHub 只在默认分支上有这个工作流文件时才允许 `workflow_dispatch`，`schedule` 只跑默认分支的最新提交。上线前没有任何票进 `site`，所以迁移工作流和监控工作流在上线合并之前既不能手动触发，也不会定时跑。
2. 于是 #40 第 5 条最早在上线合并后才能勾，#40 关不掉；而 #45 原生被 #40 卡住，推进器只领「卡点 0」的票，#45 永远领不到。卡住的是整条订阅链 #45–#51，以及下游 #53、#54、#57–#61、#66。这和第一轮 P1-5 是同一类：原生依赖图没有环，环在验收里。
3. #59 第 5 条同理做不到，评审会一直判返工（第一轮 P1-6 那一类）。
4. 生产上的角色属性没人核对：安全顾问不查 `BYPASSRLS` 和表的所有者，#45 的权限测试只在 PGLite 上跑。

改法：

- #40 删掉第 5 条。#40 做完建项目、建 `site_api`、配两个连接串、核实暂停规则就关。
- 主会话用一个 `chore/` PR 先往 `site` 放两个只有 `workflow_dispatch` 的工作流文件（迁移、监控，名字和 #45、#59 要建的一致）。之后 #45、#59 在 `feature/v1` 上改工作流内容，用 `ref=feature/v1` 手动触发，上线前就能把迁移跑进生产库、把告警演练一次。不这样做的话，就接受首次生产迁移发生在上线合并时，下面的核对挪进 P1-3 的上线步骤。推荐前者：问题在上线前暴露。
- 首次生产迁移后的核对写成一项（放进 #45 的验收，或关口四清单）：安全顾问 0 个问题；`pg_roles` 里 `site_api` 的 `rolbypassrls`、`rolsuper` 为假；`pg_tables` 里 schema `site` 两张表的 `tableowner` 不是 `site_api`；`anon`、`authenticated` 对两张表 `has_table_privilege` 为假。截图或查询输出贴票。
- #59 第 5 条改成按上面的 `ref` 触发；做不到时改成「判定脚本在会话里对一个必定失败的地址跑两次，开出一个告警 issue」，真实工作流的告警留给关口四「监控」一项（已有）。
- 规格 #19「测试决定」和 #45「测试接缝」里「生产上靠 #40 的安全顾问截图」跟着改。

### P1-2 分流的路由表漏了 Veli 的静态资源路径，#62 的验收发现不了

位置：`docs/architecture/overview.md` 路由表 Veli 一行；ADR-0003 (c) 第 2 条；#62 验收第 1–3 条；thin-muscle-coach `next.config.ts`（没有 `assetPrefix`）。

Veli 是 Next.js，页面的脚本、样式、字体和图片都从同一个域名的 `/_next/static/*`、`/_next/image` 取。路由表的 Veli 一行没有 `/_next/*`，按表配的 rewrites 会把这些请求交给主站，返回 404：经主站代理打开的 /body、/app 只有 HTML，没有脚本和样式。#62 的三条验收（逐行断言 rewrite、逐个比 HTML 的状态码）在这种情况下全部通过。这是两个仓库共用的路由表，属于 ADR 层的决定，不该留给实现的 Agent 现场发现。

改法（二选一，写进 ADR-0003 (c) 和路由表，两个仓库一起改）：

- 路由表 Veli 一行加 `/_next/*` 和 Veli 根目录下的静态文件（站点图标、清单等，逐个列出）；或者
- Veli 设 `assetPrefix` 指向自己的生产地址，静态资源不经代理。

#62 加一条验收：Playwright 经主站预览域名打开 `/body`、`/en/body`、`/app`，页面发出的请求里 4xx、5xx 为 0，脚本和样式都由 Veli 返回。

### P1-3 上线链没接上

位置：#66 做什么、验收第 1、5 条；`pipeline.md` §2.3、§5；AGENTS.project.md 第 9 条；ADR-0003 (c) 最后一条；thin-muscle-coach#185（最后更新 08:03，早于 05a527f）；#54 验收第 1 条「为什么是肌肉 → `/body` 的研究卡锚点」；`docs/delivery/loops/site-runner.md` 第 3、4 步。

2. **切换域名没人做。** 把 `velicoach.com` 从 Veli 项目解绑、挂到主站项目，是两个 Vercel 项目的账号操作。#66 标 `ready-for-agent`，实现的 Agent 做不了（第一轮 P1-6 那一类）。

### P1-4 ADR-0005 (b) 的「Pro 之后用 Vercel 告警」在 Pro 上做不到

这是要产品负责人选的一件事（只涉及 #65 和 ADR、PRD 的文字，不影响其他票）：

- (a) 推荐：Pro 之后错误告警仍走每日日报（ADR-0005 (b) 第 1 条照旧）；「挂了」由 ADR-0005 (a) 的外部探测在约 20 分钟内告警，已经覆盖整站不可用。改 ADR-0005 (b)、PRD「可观测性」一行和 #65 第 3 条。

8. #50 的删除命令没写在哪里跑、用哪个连接串。写明：在产品负责人本机用 `site_api` 的连接串跑（`site_api` 有两张表的 delete 授权和策略），不用所有者连接串；不做成 GitHub Actions 的手动工作流：仓库是公开的，运行的输入和日志谁都看得到，邮箱会泄露。
9. 迁移工作流在公开仓库里：只允许 `push: site` 和 `workflow_dispatch` 两种触发，不用 `pull_request`、`pull_request_target`；`SITE_DB_MIGRATE_URL` 放进一个要人批准的 GitHub Environment。加进 #45 的验收。
10. ADR-0005 (a) 的工作流用 `GITHUB_TOKEN` 写 issue 和评论，没有 `<!-- vc-bot role=… -->` 首行；推进器把不带它的评论当成产品负责人的回复去执行。写明工作流写的每条正文和评论都带 `<!-- vc-bot role=监控 -->`，「一个固定的 issue」写明是哪一张，不用 #13。

12. #32 备注「本票只在预览上用带 Host 头的请求验证」、规格 #18 退出条件「DNS 生效前用带 Host 头的请求验证」：Vercel 按 Host 选部署，对预览地址发 `Host: with.velicoach.com` 到不了这个预览。改成在 `node --test` 里对本地服务端发带 Host 头的请求。
13. #62 补三点：经代理的 `/auth/*` 响应里 `Location` 和登录回调地址也不带 Veli 生产部署的主机名（现在只查了 `Set-Cookie`）；rewrite 指向的 Veli 地址不在 Vercel 的部署保护后面；装过 Veli PWA 的浏览器里，Veli 的 service worker 作用域不覆盖主站的路径（写进 #185 或 Veli 的切换票）。

15. Supabase 连接池的事务模式不支持命名的预编译语句：#45 写明驱动关掉它（例如 postgres.js 的 `prepare: false`），否则生产上第一次请求就报错，PGLite 上测不出来。
16. #61 的依赖漏洞每周检查也是定时工作流，和 P1-1 同一类：上线前不会跑，「严重漏洞自动开票」在会话里改成用脚本对一份固定的 `npm audit` 输出测。

## 金字塔复核

- **结论能不能被验收支撑**：M1、M2 的规格和票能；M3 的订阅链被 P1-1 卡住；M4 的「velicoach.com 下每个地址都落到对的应用」（#20 用户故事 8）现在支撑不住，原因是 P1-2、P1-3。
- **验收之间的重叠**：#53「页面状态都能触发」和各页面票重复，作为集成核对保留；#62 和 #66 的核对脚本有重叠，P1-3 改完后 #62 管预览、#66 管生产，各自一份脚本或同一脚本两个目标，写清楚即可。
- **遗漏**：上线当天的步骤和负责人（P1-3）；生产上 `site_api` 的角色核对（P1-1）；Veli 的静态资源路径（P1-2）。
- **每条理由能不能追到 PRD 或原话**：ADR-0005 (b) 和 PRD「可观测性」一行的「Pro 之后用 Vercel 告警」建立在一个不对的前提上（P1-4）；其余取舍都追得到 PRD 第 269 版、ADR 或 `decisions.md`。
