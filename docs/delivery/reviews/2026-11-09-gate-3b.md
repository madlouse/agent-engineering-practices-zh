## P0

### P0-1 ADR-0004 (a) 的权限模型按字面实现会失效，最短的「修法」就是绕过行级安全

位置：`docs/architecture/adr/0004-subscription-storage.md` 第 15、17、64 行；#40、#45；仓库现有代码 `src/lib/db.ts` 第 8–19 行、`src/lib/auth/verify.server.ts` 第 16、21 行、`src/lib/auth/server.ts` 第 128 行；沙箱契约 `AGENTS.md`（「数据库不要在这里改」「Database ON, auth OFF 时不存个人数据」「不覆盖预置的 `src/lib` 辅助模块」）。

三处问题叠在一起：

1. **开了行级安全、又不给 `site_api` 写策略，`site_api` 自己也读写不了。** `site_api` 不是表的所有者（迁移用 `DATABASE_URL` 的角色建表），没有策略时每一行都被拒。实现的 Agent 最省事的改法是给 `site_api` 加 `BYPASSRLS`，或者直接用迁移那个所有者连接串，效果等于 service_role 绕过行级安全（AGENTS.project.md 和 Veli 的第 5 条线）。
2. **Supabase 默认给 `public` 下的新表授权给 `anon`、`authenticated`。** ADR 写「不给任何授权」，但不写 `revoke` 就还在；只靠「没有策略」挡住公开接口，少一道。
3. **`DATABASE_URL` 在本仓库已经被运行时代码占用。** `src/lib/db.ts` 读到它就在运行时连真库（不是 ADR 说的 `SITE_DB_URL`）；`src/lib/auth/*` 读到它会改变登录模块的行为（`VITE_AUTH_ENABLED` 现在是 `"true"`，Better Auth 会拿它连库）。按 #40 把 Supabase 所有者的连接串放进 Production 的 `DATABASE_URL`，运行时的每个函数都拿得到这个所有者权限的连接串，`getSql()` 也会用它，行级安全形同虚设。另外 `db.ts` 在变量缺失时静默落到内存 PGLite：生产上 `SITE_DB_URL` 配错，订阅会写进一个随实例消失的库，接口照样返回成功。

改法（改 ADR-0004 (a) 和 #40、#45 的正文）：

- 表放进一个不对外暴露的 schema（例如 `site`，不加进 Supabase Data API 的暴露列表）；或者留在 `public`，迁移里写 `revoke all on … from anon, authenticated`，再 `grant select, insert, update, delete … to site_api`，并为 `site_api` 写明策略（`create policy … to site_api using (true) with check (true)`）。两种选一种写死在 ADR 里。
- 迁移用的变量改名（例如 `SITE_DB_MIGRATE_URL`），只由 `scripts/migrate.mjs` 读；运行时只读 `SITE_DB_URL`，放在一个新的服务端模块里，不改 `src/lib/db.ts`（要改就先请产品负责人确认改沙箱契约）。写明 Vercel 没有「只在构建时可见」的环境变量，迁移凭据在运行时也可见：要么接受并写进「后果」，要么迁移改在构建以外的地方跑。
- `VERCEL_ENV=production` 而 `SITE_DB_URL` 缺失时，订阅接口返回 503，不落到 PGLite。
- #45 的验收加三条：`site_api` 没有 `BYPASSRLS`、不是表的所有者（查 `pg_roles`、`pg_tables`）；`anon`、`authenticated` 对两张表 `has_table_privilege` 为假；加一个检查脚本，运行时代码里读迁移变量的地方为 0。#40 加一条：第一次生产迁移后 Supabase 安全顾问 0 个问题，截图贴票。

## 金字塔复核

- **结论能不能被验收支撑**：四份规格的用户故事都能找到对应的验收，例外是 M3 故事 12（P2-9）和 M1 故事 12（P2-13）。

- **每条理由能不能追到 PRD 或原话**：除了 P1-2 的 IP 限流、P1-4 把监控 ADR 推迟到票里，其余取舍都追得到 PRD 或 `decisions.md`；这两处和 PRD 的字面不一样，要产品负责人知道并点头。

## 对问题 3、4 的直接回答

- **ADR-0004 和 PRD 细则、ADR-0003 是否一致**：接口路径和 ADR-0003 (a) 一致；细则第 2、3、4、7、9、11、15 条一致；细则第 6 条不一致（P1-2）；细则第 10 条和第 8 节「隐私」可能不一致（P2-9）；细则第 12 条以上线前升 Pro 为前提才一致（P1-2）。
- **service_role 和密钥**：没有用 service_role，也没有把密钥写进代码；但按现在的写法，运行时会拿到所有者权限的连接串，`site_api` 在行级安全下读写不了，实现时容易被改成绕过（P0-1）；三个密钥没有人配、定时接口没有鉴权（P1-3）。
- **两处取舍是否其实改了需求**：IP 限流是改了一条验收，要产品负责人决定；周日准点本身不改需求（PRD 已写上线前升 Pro），但 Pro 没有票负责、不卡上线，不升级就少了 F29 这个 P0，#37 的周六换篇也受影响，拆分说明没写（P1-2）。
