# 开发团队怎么搭起来

> 是什么：把 `docs/standards/pipeline.md` 定义的多 Agent 团队真正跑起来的操作手册：先准备什么、定时任务怎么建、怎样试跑、怎样往下一阶段走、日常怎么用。
> 依据：`pipeline.md`（机制，唯一来源）；Veli 仓库的同类做法（`docs/delivery/loops/README.md`、`pipeline.md` §4「先慢后快」）。
> 冲突时以 `pipeline.md` 为准；本页只写步骤。同样的步骤做成了技能 `agent-team-setup`，给以后的新产品仓库用。

## 1. 团队一览

| 谁 | 定义在哪 | 什么时候出场 |
|---|---|---|
| 4 个定时任务（主会话） | `docs/delivery/loops/*.md` | 关口三通过、#15 做完以后才建 |
| 11 个子 Agent | `.claude/agents/*.md` | 定时任务或主会话派出，用完即弃 |
| 主会话 | 和产品负责人对话的会话 | 关口三 a 的修改、拆票、写合并脚本、落实写回 |
| 产品负责人 | — | 需求类的改动；亲手做的只有付费、账号和权限设置、有没定的取舍的 PR、上线合并与域名切换的确认、内容定稿（只有模块样稿、训练指导、涉及法律、付费和对外承诺的）、观察者提的 b 类 PR（`pipeline.md` §5.1）；每周的站上内容由 Agent 评审后发布，他看摘要、事后可撤，订阅邮件发出前可以取消；社交帖子自己发；其余由 Agent 决定、开 PR，审核线评审通过后由主频道合并，日报和 #13 告知 |

## 2. 准备（#15）

1. Vercel 项目：每个分支出预览部署；构建里有类型检查和 lint；预览的登录保护关闭（需求第 104 条），页面检查在 Vercel Sandbox 里对预览部署跑，不带凭据（做法见 `pipeline.md` §7「页面」一行）；M3 订阅表单上预览之前重新打开预览的登录保护，届时另开票。
2. 集成分支 `feature/v1`：已建（11-04），#2、#16 合并后已快进到 `site`（11-09）。GitHub 默认分支改成 `feature/v1`，所有 PR 以它为 base（`pipeline.md` §5）；上线后改回 `site`（`launch-runbook.md`）。
3. 工作流：主会话的 `chore/` PR 把 `site-db-migrate`、`site-monitor`、`site-audit` 三个工作流文件放进默认分支 `feature/v1`，就能手动触发和定时运行。工作流文件只由主会话维护，票的 PR 不改 `.github/workflows/`。
4. 基线变绿：`npm test` 全过。
5. 合并脚本：主会话从 Veli 复用改写，`chore/` 分支（PR #68），按 b 类两份冷评审后合并（`pipeline.md` §5.1）。
6. 放行合并脚本：权限设置里只放行 `scripts/merge-ticket-pr.sh`，这一条保留，专供主频道代产品负责人审合时使用（`AGENTS.project.md`「不能越过的线」第 8 条），关口和门槛不变；本仓库的会话、循环和子 Agent 只开 PR，不调合并脚本。权限改动 Agent 只出草稿，合并脚本拒绝改了 `.claude/settings*.json` 的 PR。

## 3. 建定时任务

每个任务一份提示词，配置写在对应文件开头。建的时候：

| 项 | 怎么填 |
|---|---|
| 提示词 | 复制 `docs/delivery/loops/<文件>.md` 的「提示词」一节，不改写；以后改提示词先改文件，再同步 |
| 定时 | 文件里写的 `CRON_TZ=America/New_York …`，和 Veli 的任务错开 |
| 主会话模型 | 文件里写的；建的时候选不了就建完再改，观察者每天核对 |
| 仓库 | madlouse/velicoach |
| 连接器 | GitHub、Vercel；观察者另加 Claude Docs（读在线 PRD） |
| 通知 | 推送开；邮件不开 |

建完在 #13 记一条：任务名、定时、模型，和对应的提示词文件。

## 4. 先慢后快

| 一步 | 做什么 | 往下走的条件 |
|---|---|---|
| 试跑 | 只建 ① 站点票推进器，手动触发一次，做第一张票 | 整条链路走完：运行锁成对、领票评论三项齐、评审跑过检查、合并脚本没被拦、交接评论格式对 |
| 阶段 1 | 打开 ① ② ③ ④ 的定时 | 前 5 个合并的 PR 产品负责人抽查，没有要退回的 |
| 阶段 2 | 加评审清扫、清理与经验（照 Veli 的定义建） | 连续一周没有「集成分支红超过 4 小时」 |

## 5. 日常怎么用（产品负责人）

- 每天早上看 #13 的正文：今天、等你合并（只有带 `owner:merge` 的：有没定的取舍、内容定稿、观察者的 b 类；和被工具拦下的。每条写着要你判断的那一句问题，简报不合格的会标出来，`pipeline.md` §5.2）、等你决定（最多 3 条）、内容这周、关口。回复写在 #13 的评论里，一句「全部按推荐」可以批量回复。
- 每周内容：周五在 #13 看本周摘要（发布了什么、邮件里放什么）。要撤下一篇，回复「撤下 <地址>」（只认你本人账号直接在 GitHub 上写的回复，经 Claude 发的不算），或自己在那个 PR 上点 Revert；要取消这一期邮件，在发送前给「订阅邮件第 N 期」的票打 `agent:hold` 或关掉它。不操作就照常发布和发信。要定稿的只有模块样稿、训练指导、涉及法律、付费和对外承诺的内容：合并带 `owner:merge` 的 PR。
- 每周看一次观察者的机制评审。
- 要暂停：给 #13 打 `agent:stop`。

## 6. 改团队

- 加一个角色或循环：先在 `pipeline.md` 的角色表和循环表里写清负责什么、交接物、谁来查，再写 `.claude/agents/` 或 `docs/delivery/loops/` 的定义；规范篇幅在预算内（`observer.md` §5）。
- 改一个技能：只改仓库里 `.grok/skills/<名字>/`，提交后再同步到账号里的同名技能（`AGENTS.project.md`「技能」）。
- Veli 那边改了机制：观察者每周日对比，要跟就换 `pipeline.md` §9 的版本号，产品负责人合并。
