# 主站的 E2E 场景表

这份表把主站 PRD（[velicoach.md](velicoach.md)）已有的需求提炼成用户场景，每一行对应一份端到端案例（`tests/e2e/cases/`）。它不新增需求：每一行写明出自 PRD 的哪一节，和 PRD 冲突时以 PRD 为准，改了 PRD 的验收标准就在同一个 PR 里改这里和案例。

规范见生态手册 `velicoach-mono/verify/`（唯一来源）：案例覆盖 PRD、像用户一样操作、跑完看运行时覆盖率、E2E 只发现问题。案例的标题以场景编号开头（比如 `scenario("S08 切换语言：…")`），`node scripts/check-e2e-trace.mjs` 按它算覆盖率，配置在 `.velicoach-checks.json` 的 `e2eTrace`。

## 范围

- v1 主站不读登录状态、不放登录入口（PRD 第 4 节「步数预算」「v1 不读登录状态」），所以没有需要登录的场景；「导航里没有登录入口」在 S04 里验。登录、账号菜单在 v2，v2 开工补行时再列场景。
- 站稳页（`/body`）和法务页由 Veli 仓库实现（F09、F10、F11、F21 的法务正文），主站只验入口和链接目标；Veli 一侧的内容归 Veli 的 E2E（thin-muscle-coach 的 `tests/e2e`）。
- 环境：本地（构建产物的预览）写案例和调驱动；集成环境（`feature/v1` 的预览部署）跑全部场景并出运行时覆盖率；线上只跑只读的冒烟。订阅的上线开关在生产默认关，预览恒为开（PRD 第 4 节「订阅的细则」第 16 条）。
- 三种版式的宽度：手机 < 744px，平板 744–1179px，桌面 ≥ 1180px（PRD 第 8 节「多端」）。

## 不做成 E2E 的需求

这些需求不在上表，原因：

| 需求 | 出自 | 为什么不放进浏览器案例 |
| --- | --- | --- |
| 监测的 5 个自定事件、外部监控和告警 | F29；第 6 节「监测」 | 事件在统计服务一侧核对，告警由监控工具和产品负责人收到来验收，不在浏览器里 |
| 站稳页 `/body` 的导航三条约定、薄肌计划与威利介绍 | F09；F10；F11 | 页面由 Veli 仓库实现；主站的上线测试检查导航三条约定（M4），归 Veli 页面可达以后的集成测试 |
| 订阅每周发送、退信处理、欢迎邮件、删除 | F07；「订阅的细则」第 7、10–13 条 | 在邮件服务和数据库一侧，用服务端检查和发送记录验收，E2E 只验用户在页面上能做的部分（S15、S16） |
| 第 4 节「性能」的 LCP、INP、CLS 和可用率 | 第 8 节「性能」「可靠性」 | 用 Lighthouse 和外部监控量，不用案例断言 |
| 色彩对比度、玻璃材质、WCAG 全部条目 | F05；F24；第 8 节「无障碍」 | 用设计系统的 `check_page.py` 和 axe 查（`docs/standards/pipeline.md` §7），案例只验用户操作的结果 |
| 投稿、搜索、AI 记单词、睡眠与饮食预告 | F20；F26；F17；F12 | v1 不做 |
