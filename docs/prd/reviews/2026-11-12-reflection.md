# PRD 整理阶段的反思（2026-11-12）

产品负责人在需求第 92 条要一份反思总结：PRD 的完善是不是已经结束，有没有过度设计。这是主会话的回答，不是产品负责人的决定；他没有回复确认以前，这里的结论只算主会话的判断。

## 做偏了什么

1. **阶段推过了头。** PRD v2.0 在 2026-11-11 合并（PR #84）以后，主会话接着做了拆票（关口三 b）、打就绪标签，11-12 又开始试跑实施。产品负责人要的是这个阶段只做 PRD 的精简、完善、优化，不涉及实施。
2. **投入和产出不成比例。** PR #95 到 #119 二十多个 PR、十几轮复审，几乎都花在票和流程文档上。同一段时间里 PRD 从第 463 版到第 469 版，只改了几处措辞和一个票号。
3. **同一个循环转了很多圈。** 改一张票的措辞，就要复审、再评审，复审又带出新的措辞问题。
4. **根因有两个。** PRD 里混进了实现细节（「订阅的细则」第 12 条把发送任务的内部做法写了一遍）和票号，票一动 PRD 就得跟着动。收尾的 PR 里顺手换方案，每次都带出新问题。

## 值得留下的

- 订阅邮件的安全设计（ADR-0004）。
- 删除订阅记录以后 Resend 一侧怎么处理，没有按不完整的事实请产品负责人决定。
- 没声明的放宽被复审查了出来（例如拆出模板票以后上线不再等分发包）。

## PRD 是不是可以收住

主会话的判断：可以。第 469 版从头到尾重读了一遍，愿景、用户、信息架构、27 个功能点、内容框架、运营、非功能需求彼此对得上，没有发现缺口。

这次整理（第 499 版）只做减法和校正，不改需求：

- 「订阅的细则」第 12 条减重：发送任务的内部做法指到 ADR-0004 (b)，PRD 只留产品负责人和订阅者看得到的行为。
- 有任务编号的内容任务，票号只留在第 7 节一列。
- 状态写成事实：关口三 b 已过，下一步是 UI/UE 全面检查。
- 第 10 条和第 8 节「隐私」标出 Resend 一侧还没有核对完，原有的要求一个字没删；「订阅的上线开关」的条件没有改。

主会话的建议（待产品负责人确认）：以后 PRD 只因 UI/UE 检查的发现或产品负责人的决定而改。

还等产品负责人的三件输入，都不需要再设计：两个分发渠道、Resend 一侧怎么处理、律师意见。
