# 这个目录

- [timeline.md](timeline.md)：本会话里留得住的用户原句，按时间排。
- [summary.md](summary.md)：按主题汇总。不代替原句。
- [trace.md](trace.md)：需求追踪。第 28 条起（Velicoach 主站）每条原句怎么理解、落在哪、状态。
- [attachments/](attachments/)：用户随消息发来的截图。

## 收录一条输入

产品负责人的每条输入分三栏落地（`AGENTS.project.md`「不能越过的线」第 1 条）：

| 栏 | 写在哪 | 写法 |
|---|---|---|
| 原话 | `timeline.md` 一节，标题只写「## 编号」，下一行写日期和时间（ET） | 原样保留，口语、错别字、同音字都不改；只有残段就写残段，不补写 |
| 规范表述 | `trace.md`「理解与裁决」一栏的第一句 | 用产品经理的书面表达和术语表的标准术语，把原话重写成一句可执行的要求；同音字和转写错误按语义改正，拿不准的名字写进这一栏，同时列进 #13「等你决定」，确认后加进术语表的转写错误清单 |
| 举一反三 | `trace.md`「举一反三」一栏 | 这条输入代表哪一类问题；全仓库同类位置在哪（文件、规则、技能、检查）；同类位置都要改完，不改的写明理由 |

落地前先按金字塔原理定位层级和维度，找已有的相关规则，合并或升级，不另起重复的一条；能写成检查的写成检查。第 84 条起每条都要在 `trace.md` 有一行，「举一反三」一栏去掉标点后至少 10 个字，「无」「-」「同上」算空（`npm run check:voice` 查）；之前的条目不补。评审和观察者的意见同样举一反三，记在 `trace.md` 或 `docs/uiue/decisions.md`。

**原话 → 规范表述的例子**

| 条 | 原话（节选） | 规范表述 |
|---|---|---|
| 81 | 让用户确认其实要有一套对应的规则，不是什么都要用户去合并。 | 按 PR 类别分级定谁合并：票和 a 类由 Agent 合并，b 类两份冷评审后由主会话合并；只有付费、权限、没定的取舍、上线和内容定稿要产品负责人确认。 |
| 82 | 另外，里面挺多同音字或者错别字的，一定要检查一下（可能是语音识别的问题），奇怪的名字可能都要确认一下 | 文档里语音识别造成的同音字和错别字按语义改正；拿不准的人名、产品名和术语列给产品负责人确认，不猜。 |
| 83 | ……然后再提示用户去合并……不然用户根本不知道去判断什么……那就会变成胡乱合并 | 要产品负责人合并的 PR，说明最上面先写决策简报：要判断什么、事实、选项和后果、建议、风险和撤回方式；没有简报的不提请合并。 |
