# 冷评审：体验原则总纲与项目落地

> 2026-11-08。评审者没有参与研究和写作。范围：`design-bar/references/ux-canon.md`、本目录 `README.md`、`quality-terms.md`（U1、U6、U8、U9、V5、V7、T11、§4.6 X1–X6）、`velicoach-layout` §3、`liquid-glass.md` §0、`design-bar/SKILL.md` 决策原则第 7 条和第 3.6 步。依据：本目录三份研究报告。只列问题，没有改任何文件。

## 结论

**P0 两条，P1 十一条，P2 十三条。** 总纲的方向站得住：原则 3「保留承载意图的步骤」、原则 4「回应和完成分两层」、原则 9「装饰要证明自己有用」都有独立的道理，不只是附和研究。问题集中在两处：

1. **裁决机制不成立。** 「冲突时的先后」所依据的顺序，研究报告自己说过证据不足。同一个技能里还有另一份不同的优先级表。
2. **新的口子没有关上。** 「意图步不计入预算」没有封闭的定义，也没有检查，等于给「一键」开了一个谁都能用的豁免。

最重要的一条是 **P0-2**：「一键」是项目不能越过的线，现在它判不了对错。

## 核对说明

- **一手来源没有核对成。** 下面 5 个地址的 WebFetch 权限请求超时，没有拿到原文：HIG `design-principles.md`、HIG `generative-ai.md`、Anthropic `measuring-agent-autonomy`、NN/g `response-times-3-important-limits`、`vercel-labs/web-interface-guidelines` README。按工具说明没有重试，也没有绕路去抓。
- **WebSearch 只返回标题。** 它只能佐证两件事：「Claude Code 用户批准了 93% 的权限请求」这一说法存在（[Digg 转述](https://digg.com/ai/8te506p3)、[Tessl](https://tessl.io/blog/claude-code-gets-auto-mode-to-cut-approval-fatigue/)，都在讲 auto mode）；HIG 有 `design-principles` 页，WWDC 2026 有对应讲座（[HIG](https://developer.apple.com/design/human-interface-guidelines/design-principles.md)、[WWDC26 250](https://developer.apple.com/videos/play/wwdc2026/250)）。数字本身没有核对。
- **因此事实一项改成交叉核对**：拿总纲和 README 的每条引用对照三份研究报告的正文和它们自己的批判，再用评审者已有的知识找反例。下面标「事实」的问题都来自这一步。**建议在合并前由能访问网络的会话补核上面 5 个地址**，重点核对 P1-3、P1-4 涉及的原话。

## P0

### P0-1 「冲突时的先后」没有依据，而且和同一技能里的另一份优先级表打架

- **位置**：`ux-canon.md` §2；README「冲突时的先后（新增）」；`design-bar/SKILL.md`「冲突时的优先级」。
- **问题**：
  1. **依据被说过头。** §2 说「迪士尼的 Four Keys 给冲突排了先后（安全在礼貌之前），苹果把 Responsibility 放在 Delight 之前」。研究报告自己说的是：
     - D'Amaro 的原文「按这个次序列出，但没有明说是优先级」；
     - 「Keys 的『优先顺序』被说得比原文更确定」（`apple-disney.md` §3.1 D5、§3.5）；
     - R16 的顺序标的是「**自定**」。
     
     HIG 的八条原则是一张列表，研究里也没有引到苹果说「按这个顺序取舍」的原话。README 写「来自迪士尼 Four Keys 和苹果 HIG 2026 版……的顺序」，把一份自定的排序写成了有出处的结论。
  2. **两份裁决表，内容不同。** `design-bar/SKILL.md` 原有一份：「事实与硬约束 → 可访问性底线 → 核心任务 → 设计语言一致 → 个性与签名 → 细节与动效」。§2 是：「安全和诚实 → 人掌控 → 完成任务 → 看得懂 → 好看和惊喜」。前者有「可访问性」，后者没有；后者有「人掌控」，前者没有。决策原则第 7 条说以 ux-canon 为总纲，但原来那份没有删，也没有说明两者的关系。
  3. **表里有原则没有归位，也有原则一条进了两级。** 原则 8（人和 Agent 读同一份结构）没有进任何一级。原则 5 同时在第 1 级和第 2 级。原则 7「一站、不丢状态」放在「人掌控」下，归类说不通。
  4. **会被反向利用。** 「安全」没有定义，有人可以用「防垃圾订阅是安全问题」把验证码排到 X5 之上，推翻「读内容和订阅不用验证码」。
- **建议的改法**：
  - 把顺序标成「**自定**，参照 Keys 的列出次序和 HIG 的条目次序」，删掉「给冲突排了先后」这类说法。README 同步改。
  - 两份表合成一份，留在 `ux-canon.md` §2；`SKILL.md` 只保留一句引用。合并后建议是：安全（对人和他人的伤害，不含防滥用）和诚实 → 无障碍底线 → 人掌控 → 完成任务 → 看得懂 → 设计语言一致 → 好看和惊喜。
  - 九条原则逐条写明在哪一级，每条只在一级。
  - 「安全」写一句定义，并注明「防滥用」不属于第 1 级，优先用频率限制和二次确认。

### P0-2 「意图步不计入预算」没有封闭定义，也没有检查，「一键」变得判不了对错

- **位置**：`ux-canon.md` 原则 3；`quality-terms.md` U1、U6；`velicoach-layout` §3 第 28 行、第 40 行；`design-bar/SKILL.md` 3.6 第 1 条；PRD「步数预算」。
- **问题**：
  1. **谁来判、按什么判，没有写。** 「意图步」由谁标、依据是什么，都没有规定。任何超预算的步骤都可以说成「同意」或「不可逆」。「同意」本身也没有边界，Cookie 同意、勾选条款、权限请求都算吗？
  2. **四处的清单不一样**：
     - 原则 3：同意、付款、不可逆、对外发送。
     - U6：对外发送、付款、删除别人也看得到的内容、删除账号。
     - X5 和原则 8：「后果大的动作」。
     - AUI 第 3 条：「不可逆或对外有后果」。
  3. **术语没进术语表。** `docs/GLOSSARY.md` 里没有「意图步」，违反「一个词一个意思」。
  4. **旧句子还在。** `velicoach-layout` §3 第 40 行仍是「超出预算就改设计，不改预算」。研究认为这正是「最需要改的一条」（`apple-disney.md` §5.5）。第 28 行加了新规则，第 40 行没动，两句并存。
  5. **没有上限。** 一个场景可以挂任意多个意图步。
- **建议的改法**：
  - 在 `GLOSSARY.md` 定义「意图步」和「撤不回的动作」，用**封闭清单**，并给出判定方法：撤销窗口内能不能把**外部世界**恢复原状（见 P1-5）。U1、U6、X5、原则 3、原则 8、AUI 表只引用这个术语，不再各列一份。
  - 加一条上限：每个撤不回的动作最多 1 个意图步；一个场景里的意图步超过 1 个时，要在 `decisions.md` 写明理由。
  - 步数表加一列「类型」。新增意图步要由设计评审在表上签字，或者在 PRD 步数表里写明对应的撤不回动作；写成脚本时，校验每个意图步都指向清单里的一类。
  - 把第 40 行改成「超出预算先删可删步；剩下的意图步按清单标明，不算超预算」。

## P1

### P1-1 「浏览器 Agent 先读无障碍树」「对人无障碍，对 Agent 就可用」说过头

- **位置**：`ux-canon.md` §0、原则 8「为什么」；`quality-terms.md` §4.6 导语。
- **问题**：
  1. **事实**：这句话来自 Claude 浏览器工具的文档和 web.dev，不是所有 Agent 都这样。OpenAI 的 Operator 和 CUA 公开说明的是以截图为主、按像素操作，这是现成的反例。
  2. **逻辑**：无障碍是必要条件，不是充分条件。验证码、登录墙、状态不在地址里、机器人拦截都和无障碍无关，原则 8 自己后面也列了这几项。「对人无障碍，对 Agent 就可用，所以这一组只放无障碍没管到的」在同一句里自相矛盾。
- **建议的改法**：改成「主流浏览器 Agent 读无障碍树、DOM 和截图中的一种或几种；无障碍是 Agent 可用的**前提**，不是全部」。出处写明是哪几家。

### P1-2 打了 ✓ 的规则大多还没有检查，而第 5 节第 2 条要求「先写成检查再出稿」

- **位置**：`ux-canon.md` §1 的 ✓ 和 §5 第 2 条；`quality-terms.md` V7、T11、X1–X4。
- **问题**：
  1. **检查还不存在。** 打 ✓ 的有「可打断」「AI 标识」「主要状态写进地址」「原生控件」「机器可读件由内容数据生成」「数字由代码给出」「材质有性能预算」。实际情况：
     - 仓库里找不到 `data-origin`；
     - eslint 的 `jsx-a11y` 规则还没开（README 列为待做的票）；
     - 语言进地址的往返测试不存在；
     - V7 的「可打断」只有设计评审在查；
     - 性能预算没有自动检查。
     
     这次落地真正新增的检查只有 `verify_canvas.py` 的「笼统的进度文字」。
  2. **门槛没人能遵守。** 照 §5 第 2 条，现在所有画板都不能出稿；照实际做法，这条门槛已经形同虚设。这违反「guardrails 要有程序性检查才算有效」。
- **建议的改法**：
  - ✓ 改成三态：「已有检查（写脚本名）」「有票待做（写票号）」「只能人判」。
  - §5 第 2 条改成「✓ 而且已有检查的必须通过；有票待做的在评审报告里逐条列出」。
  - `quality-terms` 每条「怎么查」写真实存在的东西，没写成的标「待做 #票号」。

### P1-3 93% 出处标错，推论也没有限定

- **位置**：`ux-canon.md` 原则 5「为什么」和「主要出处」。
- **问题**：
  1. **事实**：93% 来自《How we built Claude Code auto mode》（`vercel-shopify-claude-openai.md` A-3），不是「Anthropic 自主度实测」（measuring-agent-autonomy）。
  2. **两份研究的转述互相矛盾。** `vercel-shopify-claude-openai.md` §3.2 A-5 说：「复杂任务上 Claude 主动停下的次数是简单任务的两倍多」。`agent-ui.md` §1.2 说：「复杂任务上 Claude 主动停下来问的次数是人打断次数的两倍多」。两句不能都对。
  3. **推论没有限定。** 93% 的批准率说明请求大多是正常的，不能单独证明「人不读就点」。研究也写了这是开发者数据，「不能直接照搬」（§3.4）。总纲没有写这条限定。
- **建议的改法**：
  - 改正出处。
  - 补核原文，把「两倍多」统一成原话的意思。
  - 在原则 5 加一句：「数据来自开发者；大众产品的确认处更要写清后果和能否撤回」。

### P1-4 迪士尼 Lightning Lane 被用来支持「保留意图步」，而它真正的教训「负担挪出关键时刻」反而没进总纲

- **位置**：`ux-canon.md` 原则 3、§0；README 逐条判定的「一键」行。
- **问题**：
  1. **证据用错了地方。** 研究对 Lightning Lane 的结论是「把规划负担塞进体验当天是错的」，而且它自己说这类证据不一致（`apple-disney.md` §3.5）。这条说的是把负担挪到关键时刻之外，和「确认意图」不是一回事。Apple Pay 的例子也要说准确：Face ID 把「验证身份」和「确认意图」拆开了，原来按指纹一个动作同时完成两件事。准确的说法是「自动化拿掉了隐含的意图信号时，要补一个明确的」。
  2. **定义和规则对不上。** §0 把负担定义成五项（读的字、做的决定、记的东西、等待焦虑、出错代价），但规则只数步数。「关键时刻里要做的决定数」（研究的 R19、U1 的建议）没有采纳，也没有写理由。
  3. **漏掉了 Veli 的核心模式。** 威利「在用户想到之前把这一天安排好」，正是 R19。总纲漏了它最贴近 Veli 的一条。
- **建议的改法**：
  - 原则 3 的出处只留 Apple Pay，并改用上面的准确说法。
  - 新增一条原则，或者在原则 3 下补一条：「准备挪到关键时刻之前，关键时刻里要做的决定 ≤ N 个」。N 由项目落数值。
  - 至少在 README「没有采纳的」里写明理由。

### P1-5 「可撤销」按界面状态判，没有按外部后果判；撤销窗口也没有数值

- **位置**：`ux-canon.md` 原则 5、§3 AUI 第 3 条；`quality-terms.md` U6。
- **问题**：
  1. **反例一**：Agent 改了今天的训练，用户已经照着练了；提醒已经推送、已经被看到。界面上能「撤销」，现实撤不回。
  2. **反例二**：Gmail 的「撤销发送」证明，「对外发送」可以用延迟加撤销来代替确认。U6 把对外发送一律列为必须确认，过严。
  3. **研究指出的张力没有带进来。** 研究写过「乐观更新只能用于能回滚的本地状态」（`vercel-shopify-claude-openai.md` §1.5），总纲没有吸收。
  4. **判不了。** U6 没有撤销窗口的时长。AUI-3 的「10 秒（自定）」也没有带过来。
- **建议的改法**：
  - 定义成：「撤销窗口内效果不外泄（没有发出、没有被他人看到、没有被用户照着执行），才算可撤销」。窗口时长由项目落数值，例如 ≥ 10 秒，标自定。
  - 对外发送可以用「延迟 + 撤销」代替确认。
  - 乐观更新只用于可撤销的动作。

### P1-6 「主要状态写进地址」引错了出处，而且和隐私冲突

- **位置**：`ux-canon.md` 原则 7；`quality-terms.md` X1。
- **问题**：
  1. **事实**：W3C《Cool URIs don't change》讲的是地址长期不变，还建议地址里不放「状态」，原意是文档状态。它不支持「把界面状态写进地址」，这条的出处应是 Vercel WIG。
  2. **缺一个反例**：搜索词和筛选写进地址后，会进浏览历史、Referer、统计和分享出去的链接。Veli 的健康筛选、敏感搜索词就是现成的例子。
- **建议的改法**：
  - 出处换成 Vercel WIG。Cool URIs 留给「改地址一律 301」（现在 X 组缺这一条，见 P2-10）。
  - 加一条例外：「涉及健康和个人数据的状态不进地址，也不进统计」。

### P1-7 原则 6「数字和安全判断由代码给出」是 Veli 的架构规则，被提升成了通用体验原则

- **位置**：`ux-canon.md` 原则 6；`quality-terms.md` T11。
- **问题**：
  1. **越界**：这是 Veli `AGENTS.md` 第 1 条的架构约束，不是界面可观察的规则。通用产品里，模型给出带出处的数字也可以是合理设计。
  2. **项目内放错了位置**：T11 把它和「AI 内容标识」捆在一条里，规则不单一；适用范围写「全站和 Veli」，但 Veli 以自己的设计系统为准，主站的规则表管不到 Veli。
- **建议的改法**：
  - 总纲改成「后果严重的数字和判断（健康、金钱、安全）要么由确定性来源给出，要么标明来源和把握」。
  - T11 只留标识，适用范围写「主站」；「数字由代码给出」留在 Veli 的规范里。

### P1-8 ux-canon.md 混进了 Velicoach 专有的内容，数值也越过了它自己的分工

- **位置**：`ux-canon.md` 第 4–5 行、原则 7、原则 8、§3 导语、§4「悬停 80ms」；`liquid-glass.md` §0 第 3 条。
- **问题**：第 4 行说「项目只写项目的数值」，言下之意是数值归项目、原则归总纲。可总纲里有：
  1. **项目路径**：第 5 行「逐条出处和批判见 Velicoach 仓库 `docs/uiue/...`」。复用到别的仓库时，这是一条死链。
  2. **项目口号**：原则 7「完成旅程不离开本站、不再登录」是 Velicoach 的「一站」。一般产品跳到第三方登录、付款、文档都是正常的，通用的说法是「跨产品跳转时带上下文，不重复登录」。
  3. **项目功能**：原则 8 的「订阅」。
  4. **项目自己的数**：§4 的「悬停 80ms」是 Velicoach 自定的数，不是行业说法；`liquid-glass.md` §0 的「中端安卓机 INP ≤ 200ms（自定）」也是。
  5. **项目例子**：§3 导语「例如 Veli 的威利」。
- **建议的改法**：
  - 第 5 行改成「项目在自己的仓库里留一份复核记录」。
  - 原则 7 改成通用说法，「一站」留在 Velicoach 的 U7。
  - 原则 8 的「订阅」改成「读内容和低风险的表单」。
  - §4 删掉 80ms 一行，搬到 README。
  - liquid-glass 的数值改成「性能预算由项目定，例如……」。
  - 有出处的默认值（0.1 秒、150–300ms）可以留，标明是默认值和出处。

### P1-9 quality-terms.md 改成六个维度后，组合词和章节标题没有跟上

- **位置**：`quality-terms.md` §2.2、§4 标题、第 6 行版本、§8。
- **问题**：
  1. **组合词的定义漏了 X 组。** §2.2「体验友好：**五个**维度里……全部通过」，§4 标题还是「五个维度的规则」，§1 和 §2.1 写的是六个维度。体验友好算不算 X 组，现在说不清，而它是验收最常用的组合词。
  2. **版本没升。** 第 6 行仍是「第 2 版（2026-11-04）」，这次改了 6 条、新增 7 条，没有版本记录。
  3. **新词不受检查。** X 组收的词（对 Agent 友好、Agent 友好、机器可读）没有加进 §8，`check:vague` 不会拦它们。
- **建议的改法**：
  - §2.2 和 §4 标题改成六个维度，并写明 X 组只在关口四查（和 bar-sheet 一致）。
  - 版本升到第 3 版，列出改动。
  - §8 补上这三个词。

### P1-10 X4 写了 llms.txt，而 §4.6 导语说新协议不进规则

- **位置**：`quality-terms.md` §4.6 导语和 X4；`ux-canon.md` 原则 8（llms.txt 打了 ✓）和 §4。
- **问题**：导语说「新协议（llms.txt、WebMCP）还在提案阶段，不进规则」，X4 却要求「`llms.txt` 由内容数据生成」。原则 8 把它列成 ✓，§4 又说「顺手做」。三处口径不一样。
- **建议的改法**：统一成「llms.txt 不是规则；做了的话由内容数据生成」。把它从 X4 的必查项里拿掉，改成「如果有」。

### P1-11 Agent 失败时的恢复和个人数据授权，总纲缺规则

- **位置**：`ux-canon.md` §3。
- **问题**：
  1. **失败恢复**：§3 有「停止」和「断点续做」，没有失败时怎么办：做到哪了、哪些已经生效、哪些没有、怎么补救或回滚、是 Agent 的错还是服务的错。HIG 的「AI 不可用时仍然能用」（`apple-disney.md` §2.3 第 9 条）和「完成时附证据」（AR6）也没有进来。
  2. **授权**：只有「记住了什么能看、能删」。没有授权的范围、期限、随时撤回、按站点或数据类别授权（Claude for Chrome 的做法）。对读健康数据的 Veli，这是最重的一条。
- **建议的改法**：§3 加三条，并写明检查方法：
  - 「Agent 失败或中断时，列出已生效、未生效、怎么补救，给一个不经过 AI 的后备路径」（端到端）；
  - 「Agent 用到个人数据前，按类别请求授权，写清用途和期限；授权页能随时撤回，撤回后下一次行为不再用」（端到端）；
  - 「Agent 说完成时附证据」。
